## 1. 树的手术（先改结构，再谈文档格式）

对每个子项目逐条判：

| 情形 | 动作 |
|---|---|
| 涵盖多个点 | **拆** |
| 与另一项雷同 | **合并** |
| 前提/接口互相冲突 | 合并，或删其一 |
| 毫无意义 | **直接删** |
| 只是业界已做透的传统方法 | 降级为「参照/基线」，**不作为子项目** |

**创新判据（最重要）**：子项目必须对准一个 **innovative 设计**——相对普通
decoder-only transformer 改了什么、预期带来什么效用。**不重做业界已做透的东西**；
业界的成熟做法只作为「必须打败的基线」引用（站在巨人肩上）。

## 2. 每个子项目的文档：YAML（不是 Markdown）

每个子项目目录下**一份 YAML**（文件名与目录布局待裁，见 §5）。字段至少：

| 字段 | 含义 |
|---|---|
| `id` | 子项目标识 |
| `purpose` | 这个子项目是干什么的（一句话） |
| `innovation` | 尝试引入的 innovative 设计（相对 stock 改了什么） |
| `expected_effect` | 这个创新设计的预期效用 |
| `validation` | 该效用如何做**端到端**验证（判据 + 对照 + 口径） |
| `cost_model` | **不用墙钟**；等效理论时间/计算量降低（FLOPs / layer-passes / tokens-per-forward 等），并**考虑 pipelining** |
| `status` | 最新状态：未开始／进行中／已完成／被否证 |
| `conclusion` | 结论 |
| `conclusion_review` | 这个结论看上去对吗（自评 + 复核） |
| `experiments` | 做了哪些实验（指向实验目录） |
| `argument` | 是怎么论证的 |
| `gaps` | 有没有遗漏什么 |
| `started` / `ended` | 起止时间 |
| `change_log` | 变更记录 |

## 3. 状态汇总脚本（不是 build）

写一个**小脚本**扫描所有子项目 YAML，输出一张表：

`id / 何时开始 / 何时结束 / 是否完成 / 当前状态 / 结论 / 结论看上去对吗 / 做了哪些实验 / 如何论证 / 遗漏什么`

要求：**不要网页、不要 build、不要缓存、不要 fancy**。

## 4. 验收标准

1. 子项目树做过拆分/合并/删除，且每一项都满足 §1。
2. 每个子项目有一份 YAML，§2 字段齐全。
3. 汇总脚本能一条命令跑出全表。
4. `catalog.yaml` / `build_wiki.py` / `check_schema.py` 的去留一并裁决（见 §5）。
