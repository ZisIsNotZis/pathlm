## 0 人话摘要（先读这段）

这一轮里，六个研究大类各自做完「认人 + 想清楚 + 跑一个最高价值实验 + 独立复核」。因为大家
**独立**工作，会碰到一些**同一类**、且**越出单个研究项**的问题——比如「用哪个噪声带去判两个数字
谁高谁低」「基线到底算不算数」「能不能动共享代码去测完整机制」。按纪律，这类问题**执行方不许自选**，
必须上报出资人。本文把散在六个工单里的这些问题收成一张表。

**最集中的三件事**：

1. **「0.014 噪声带」到底能不能当判决阈值？** 几乎所有轴都被它绊到。它原本只是「13M 模型换随机
   种子重跑，bpc 会漂多少」的一个**经验带**，现在却被当成「两个结果谁高谁低」的通用门槛——但
   **量纲不对**（对概率/接受率类指标尤其明显），而且它本身来源还自相矛盾。**待裁决。**
2. **milestone 的验收口径要不要收紧？** 轴 2 出现「按预登记文字（Δ ≤ 0.014）算**过关**，按实质
   （相对同算力最强固定深度**不差**）算**不过关**」的分裂。要不要把验收线改成「相对同算力前沿不差」，
   **待裁决。**
3. **共享引擎能不能动？** 三个轴（1/3/6）都发现「不扩建共享引擎就测不了完整机制」，都**没有擅自改**，
   把最小 patch 报了上来。**是否授权、谁改、谁复核，待裁决。**

另外：旧 wiki / catalog 退役已在迁移里执行完（归档不删），请知悉/追认；`role_map` 实名已在 M3 补齐。

**统计**：本文件共收 **21 条**——**跨轴共性 5 条**（§2 表 A，C1–C5）+ **各轴独有 16 条**（§3 表 B：
轴 1 ×3、轴 2 ×3、轴 3 ×2、轴 4 ×2、轴 5 ×4、轴 6 ×2）。其中 C1–C4 汇总了轴 1/3/6 的 F1/F5 等
共性项；各轴的完整 F1–Fn 见对应 `TICKET.md` §4/§5/§10。

## 2 跨轴共性取舍（表 A）

### 2.1 C1 · 0.014「噪声带」是否可当判决阈值

- **来源**：ticket 56 §8.6.4（M2 遗留未决第 4 条）；轴 1 `62/TICKET §4-F1`；轴 2 `61/TICKET §5-F2`；
  轴 3 `64/TICKET §4`（判据带）；轴 4 `65/TICKET §4`（判据带）；轴 5 `66/TICKET §10-F1`；
  轴 6 `63/TICKET §4-F1`。
- **问题**：`docs/methodology.md` §2 把 **0.014** 定义为「13M 模型跨 run 的 **bpc** 漂移界」（一个
  经验方差带）。但多个轴把它当成「两个数字谁高谁低」的**通用可排序门槛**用时越过了它的量纲：
  - 轴 6 直接点破：同文件 `:25-28` **明文**写「0.014 是 **bpc** 口径方差带、**不得**直接当准确率的
    1.4pp 界；准确率用**二项 / Wilson 95% CI**」。轴 6 用它判接受率 α₁/τ 属**跨量纲借用**。
  - 轴 5 实测单臂跨窗口极差为 **0.036324**（远大于 0.014），故它改用本格「在力带」，并声明两带
    不得混用。
  - 轴 1 的 carry 臂间差 **+0.0031/+0.0025**：大于本格自测 σ_cell=0.00166、远小于 0.014 ⇒ 按
    0.014 判「不显著」、按本格换种子极差判「显著」，两读法结论相反。
  - 轴 3 判 `3.1.4` 的 `|Δ|=0.0021 ≪ 0.014` 判「不可排序」；轴 4 直接以 0.014 为判据带。
- **各轴默认处置**：一律**双列并报**（给出 CI / 本格 σ，同时标注与 0.014 的关系），**不自选阈值**。
- **影响面**：全树所有「该不该算显著」的判断，尤其**跨量纲**（bpc vs 准确率/接受率）与
  **跨格**（单臂跨窗口极差 vs 跨 run 漂移）两类比较。
- **待裁决点**：
  1. 0.014 **仅**限 bpc 口径、且仅在「配对 Δ、≥5 窗口」条件下可作参考门槛；
  2. 概率 / 接受率类指标**单独定门**（建议：按 prompt 聚类的 bootstrap / Wilson CI 不含 0 为主判）；
  3. 单格自测带与跨格 0.014 的关系与优先级；
  4. 是否要求 `falsification` 字段显式声明「用哪个带」。

### 2.2 C2 · milestone 验收口径是否收紧为「相对同算力前沿不差」

- **来源**：轴 2 `61/TICKET §5-F5`（+ report §4.5）；轴 3 有同族现象（`3.1.4` 判决「总量是旋钮、
  分配不是」，判据带 0.014）。
- **问题**：`2.1.1` 的 milestone 验收文字是「至少一条策略**省算力且 Δ ≤ 0.014**」。本轮实测里
  τ≥0.99 档**省 6–12% 且 Δ ≤ 0.0002** ⇒ 按**预登记文字**算**过关**；但同算力的「固定跑前 k 层」
  比它更好 ⇒ 按**实质**（相对同算力最强固定深度**不差**）算**不过关**。两种读法给出相反验收。
- **各轴默认处置**：不改预登记 milestone 文字（预登记契约），在 `conclusion` 里**同时写明「字面成立 /
  实质否证」**，把是否收紧口径留 Main 裁。
- **影响面**：所有「用更少算力拿类似质量」类研究项的**验收线定义**（1.1.4.1、2.1.1、3.1.x、4.x、
  5.x、6.2 等）；取决于是否接受「相对同算力前沿不差」作为统一实质判据。
- **待裁决点**：是否把验收口径从「Δ ≤ 噪声带」改为「相对**同算力**前沿的超出量 ≤ 0」（即不允许
  被同算力的朴素方案支配），以及该口径是否写入 `docs/research-schema.md` 的 `milestone.acceptance`
  纪律。

### 2.3 C3 · 是否授权改共享引擎（`pathlm/**`）

- **来源**：轴 1 `62/TICKET §4-F5`；轴 3 `64/TICKET §4-F2`；轴 6 `63/TICKET §4-F3`。
- **问题**：三轴都撞到「不扩建共享引擎就测不了**完整机制**」（测出来只能是被引擎能力削过的退化版）：
  - 轴 1：`CarryChannel` 目前是**单共享槽**（一个状态覆盖 12 层、只从输入流写）；完整机制需
    **逐层独立状态 + 内容相关写入门**。最小 patch ≈ 60–120 行、只动 `pathlm/depth_ar.py`。
  - 轴 3：引擎 `mlp_mult` 是**全局标量**、无「逐层 FFN 宽」开关；已在**实验目录内**用前缀切片绕过
    （等值性门证明与引擎原生窄 FFN 逐位同前向），但「逐层宽度」开关本身需引擎。
  - 轴 6：完整二级树（N+3 以被接受的 N+2 候选为条件）需**新的二级条件头 + 重训**。
- **各轴默认处置**：**一律不擅自改** `pathlm/**`（边界纪律），只交「需要什么 + 为什么 + 最小 patch
  描述」，上报 Main。
- **影响面**：完整机制能否被端到端验证（关系到是否会把「机制不成立」误判成「实现不成立」）。
- **待裁决点**：是否授权、**谁改、谁复核、是否本轮做**；授权后按 `SCHEMA.md` §22 代码编辑锁 +
  §14/§14b 复核顺序执行。
