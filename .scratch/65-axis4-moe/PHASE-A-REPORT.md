## 0. 人话摘要（先讲人话，再给数据）

MoE 是**业界已经做透**的路线（Switch / GShard / Mixtral / DeepSeekMoE 都在论文里做完了）。按出资人纪律，
本轴最大的风险不是「会不会做 MoE」，而是**造轮子**——所以本轴三格都必须写清一件事：**相对巨人，我们多做的事是什么**。

这一轮（Phase A）我干了三件事：

1. **把三格的定义写清楚了**：4.1 稀疏激活专家、4.2 路由与负载均衡、4.3 专家粒度/异构。
   每一格都补了「相对 SOTA 的增量」（不是「实现一个 MoE」）、把 SOTA 出处换成**联网核实过的 arXiv 编号**
   （以前写的是「记忆·未核」，因为之前环境查不了网）。
2. **把尺子做好了，还没量**：13M 这个尺度上，一个普通模型 1360 万参数、每过一个 token 前馈层做 944 万次乘加；
   换成「8 个专家、每个 token 只走 1 个」（top-1）后，参数涨到 **7980 万**，但**每 token 的乘加数和普通模型一模一样**
   ——这就是 MoE 想卖的东西：**同样的算力，8 倍的参数存量**。我另外配了两个「参数一样多但一直是普通 dense」的
   对照臂，用来分辨「涨的是 MoE 结构的功劳，还是单纯参数变多」。同时证明了这套 MoE 接线是**透明的**
   （设成 1 个专家、把普通模型的权重灌进去，输出**一位不差**）而且**是活的**（路由器梯度非零、真的会选不同专家）。
3. **顺手回答了 55-review 的一个质疑**：它问「13M 这么小，负载均衡到底有没有意义」。我跑了一条单臂探针
   （13M、top-1、**不带**均衡机制、1200 步）：**路由根本没有坍缩**——专家使用率的归一化熵全程 0.952–0.983
   （最大 1.0），最大占比全程 0.178–0.214（均匀是 0.125），而且**没有往下走的趋势**（斜率 ≈ +0.000015/步）。
   只有一点温和、持久的偏斜（专家 3/7 长期拿约 1.3–1.5 倍份额）。
   含义：**在 13M / 1200 步这个口径下，「均衡机制去修坍缩」这个故事没有对象**；4.2 的价值得改从
   「它是否提高质量」去量，不能靠「它修好了坍缩」立论。

一句话结论：**尺子做好了、接线验证过了、一个前提被证伪了；真正量 MoE 值不值（13M 三臂）还没做，需要 GPU 训练，
成本和做法已经写死（§4）。**

### 1.3 坍缩可观测性探针（4.2 前提；单臂、非判决）

## 4. 剩余 / 受阻项与下一步

**未满足的判据（如实登记，不谎报 PASS）**：4.1-WP1 / 4.2-WP1 / 4.3-WP1 的质量判决均未做。

**为什么本阶段不做 13M 训练判决（已确证不可行，不是懒）**：
- 前置（臂定义 + 代价 + 接线）必须先钉死 ⇒ 本 WP 已做死；
- 13M 单臂**实测步时 ≈0.75–1.15 s/步**（争用下），6000 步 ≈ 75 min/臂；三臂 + n≥2 seed 远超 1.5h 时间盒；
- 实测步时须**开跑前先测 20 步再定预算**（§17.8），这条路径留给下一阶段。

**下一步最小实验 + 等效算力成本**：
- **4.1-WP1**：13M matched-step，`{dense-B0, moe-top1-E8, moe-top2-E8}` + 等参数对照，n≥2，
  报 clean bpc + 专家 MACs/token + 参数量 + 使用率分布（逐层）。**等效训练算力** = 3 臂 × 98.3M token ×
  （与 dense-B0 同量级的前向+反向）；等参数对照臂自带 8×/4× 每 token 算力，须单列。**开跑前先测 20 步定预算**。
- **4.2-WP1**：均衡四臂（朴素 top-k / aux loss λ 扫描 / capacity factor / expert-choice），k 与总参数逐位对齐，
  报使用率分布 + 跨 seed 翻转率。**注意**：本阶段探针已表明「修复坍缩」不是有效判据 ⇒ 判据应改成
  「均衡是否提高质量 / 降低偏斜」，否则是无对象判据（已写进 4.2 的 `falsification`/`conclusion`）。
- **4.3-WP1**：固定总参数与每 token 激活算力，{粗粒度, 细粒度, 细粒度+共享专家} 三臂。

**上报 Main 的框架性取舍（本轴不自选）**：
1. **13M 尺度是否值得花 GPU 做 MoE 判决**：探针显示该尺度下负载均衡无对象（路由不坍缩），且 `tokens-per-param`
   1.23–2.34 处于严重数据受限区。是否：① 仍在该尺度跑 4.1-WP1（诚实对手 = 等 FLOPs dense）；
   ② 把 MoE 判决降为参照（按 55-review W-03/W-04），只保留「本仓等效代价口径下的取舍」记录；
   ③ 换更大 token 预算（如 600M ≈ 6× 等效算力）让 `tokens-per-param` 对齐。
2. **GPU 争用**：本阶段取锁期间卡已被两个**未持锁**的外部进程占 12.9GB/90%；后续训练判决的排期需 Main 协调。
