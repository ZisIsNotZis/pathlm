## 2 到终局的一项：`1.1.3 可见量上限`

- **判词（人话）**：「可见量上限」不是本仓的一根独立旋钮——限制「每个 token 最多看多少」只有两个开关
  （按位置的窗口/锚点掩码，属 `1.1.1`；按内容的 top-k，属 `1.2.3`），两者互斥（引擎里硬报错）
  ⇒ 按本项预登记验收的「若否」分支：**建议并入 `1.1.1`**（树级动作待 Main 裁，见 ticket F12）。
- **但它问的子问题有数据答案**：质量随上限单调可排序（k=16→128 的 clean bpc `1.628110 → 1.513325`，
  降 `0.114785`，越 0.014 带；评测期「只留最近 k」另一条口径 192/128/64/32 = `+0.004175 / +0.020065 /
  +0.080508 / +0.211815`）；**召回不随上限变**（k=16 的窗外针停在同掩码地板；k=192+8 锚点时
  「整段落在窗外」的 494 根针差恰好 `0.000`）⇒ 加宽可见量买到的是**局部统计**，不是把远处信息搬近。
- 让人话量级落地：把可见量从 16 加到 128（可见量 ×8，仍是 T=256 的一半）换来 0.114785 bpc，
  相当于把「窗口 16 → 全量」那 0.125421 的差距**补掉 91.5%**（我的算式：0.114785 / 0.125421），
  而**窗外召回一点没动**——这就是「质量来自局部统计、不是远处信息」。
