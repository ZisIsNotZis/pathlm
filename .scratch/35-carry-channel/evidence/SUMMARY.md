# SUMMARY — ticket 35 · 第八批（制造需求 + 提供通道）——**首个正面结果**

## 零、人话摘要（先读这段）

**这一批回答了你最初的问题：「信息到底能不能往右搬？要怎么做？」答案是：能——但必须同时
给它「需求」和「通道」，而且写入规则要用「只搬增量」。**

**做法**（我们第一次真的能测这件事）：
1. 换掉 enwik8，改用**合成关联回忆任务**（给 key 问 value）——因为实测证明我们的模型在
   enwik8 上「不需要」长程信息，之前测不出东西是任务不对；
2. 用**窗口 16** 制造需求：key 全部落在窗外（实测距离 241–255，**100% 在窗外**）；
3. 提供一条**显式写入通道**（一个共享记忆槽，每层用自己的 query 去读），比较三种写入规则。

**结果（三臂，13M、12k 步、逐位等参数、唯一变量 = 写入规则）**：

| 臂 | 关联回忆准确率 | 读数 |
|---|---|---|
| **U0 无通道** | **0.0137**（CI 上界 1.77%） | ≈ 随机（1.56%）⇒ **前提校验通过：不搬就真答不出** |
| **U1 plain 累加写** | 0.0007 / **0.0334**（两次） | **双稳态**（同配置同 seed 两次差 3.27pp）⇒ 不稳定，弱 |
| **U2 delta 写**（只搬增量） | **0.0950**（6.08× 随机） | **+8.13pp vs U0，置信区间不重叠** |

**三条护栏全部通过**（这是我最担心的部分）：
- **毁源对照臂**：把源片段内容毁掉后，U2 从 9.50% **掉到 0.81%**（低于随机）⇒ 这个读数
  **确实来自「被搬过去的信息」**，不是从窗口内线索猜的；
- **因果性**（本设计最致命的 bug 源）：分块实现与顺序参考在 fp64 下 **<1e-12 逐位一致**、
  扰动后段时前段输出 `torch.equal`、读后写约定有专测、**故意制造未来泄漏的变异被抓红**；
- **等参数**：U1/U2 **188 个张量逐位相同**（13,801,064 参数），唯一差异是写入式。

**顺带一个有意思的**：delta 写得稳、plain 累加写不稳——这与业界在关联回忆上的已知结论一致
（累加写会让记忆互相覆盖，delta 写修正这一点）。我们等于在一个**可对照的标准设定**上验证了它。

**边界（防止过度解读）**：绝对水平只有 **9.5%**（13M/12k 步）⇒ 只能读作「在该任务/该尺度上
成立」，**不得**外推成「业界做不到/做得到」；plain 的双稳态使「delta 优于 plain」只算
「在两支读数上成立」，不作强结论；距离曲线非单调（受训练位置结构混杂），不外推。

## 二、实现决策（SCHEMA §17.8，如实记账）

- **单共享记忆槽（主 Agent 批准）**：per-layer-12 实装实测 **221/410 ms/step**（超预算 2.4×），
  根因是**算子派发与 autograd 节点开销**（~1000 算子/步、~2500 节点），**不是 FLOPs**。
  改用单槽后落回预算内，且**正好对齐 MQAR / 线性注意力的标准形态** ⇒ 读数可与既有做法对照。
- 代价：写入从输入流（而非各层隐状态）出发，表达力较弱；`+264,296` 参数（U1/U2 逐位相同，旁路）。
