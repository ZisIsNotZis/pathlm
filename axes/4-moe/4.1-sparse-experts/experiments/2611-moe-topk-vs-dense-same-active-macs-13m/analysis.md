# 2611 · 同每 token 激活 MACs 下「稀疏激活专家」买不买得到质量（`4.1` 的判决实验）· 分析

## 0 人话摘要（结论先行）

**一句话**：在**每 token 花同样多的前馈算力**的前提下，把 FFN 拆成 4 个或 8 个「每 token 只走 1 个」的
专家，在 13M / 98.3M token 这一格上**买不到可测的质量**——两个 seed 的配对差都落在 0.014 bpc 的噪声带内，
而且多出来的参数（3.09× / 5.87×）把 token/param 从 7.23 压到 2.34 / 1.23。

**六问逐条**：

1. **它是干什么的**：普通 transformer 的 FFN 是「全参数都过」的，所以「模型容量（参数）」和「每 token 算力」
   绑在一起。稀疏激活专家（MoE）的卖点是把这两件事解开：参数 ×E、每 token 只算 1 个专家。本格要判的就是
   **这笔「多出来的容量」能不能兑现成质量**——而且只在**同每 token 激活算力**下判，因为同参数比 MoE 必胜。
2. **相对普通 decoder-only 改了什么**：只改 FFN。每层 `Block.mlp` 换成「E 个同宽专家（`h_e=1536`，与 stock
   的 `mlp_mult=6` 同宽）+ 一个 `d×E` 路由器」，每 token 只过 top-1、权重归一到 1.0；注意力 / LN / embedding /
   读出 / 层数 / 残差一字未动，同 seed 下 MoE 臂的非 FFN 参数从 stock dense 臂**逐位拷贝**。无负载均衡辅助损失
   （均衡属 `4.2`，本格只判 top-k 本体）。
3. **为什么要改**：这是业界唯一被大规模验证的「保容量减算力」路线（Switch / GShard / Mixtral / DeepSeekMoE）。
   本格不是把 Mixtral 重跑一遍，而是给出**小尺度、单卡、单文件数据**下「每 token 专家 MACs → (clean bpc, 总参数,
   专家使用率)」三列同框的数字，并把**等激活算力**与**等参数**双对照都钉住。
4. **怎么测的**：13M 基底（`d=256 / L=12 / H=8`）、enwik8 字符级、6000 步 × bs32 × T=512 = **98,304,000 token/臂**、
   seed 0 与 1；20 批 × bs16 的**配对** clean bpc（末 10M 留出、fp32、无 autocast、同 `window_seed` ⇒ 全臂逐批同窗）。
   8 臂：`dense-B0`（主对照）、`moe-top1-E4`、`moe-top1-E8`（两个实验臂，专家激活 MACs 与 dense **逐位相等**）、
   `dense-eqparam-E4`（等参数旁证，4× 激活算力，**不参与主判**），各 seed 0/1。判据线跑前预登记并绑定
   （`prereg_binding.json`，六次重绑的逐条披露见 §3 与 `README.md` §10）。
5. **测出来多少**（Δ = bpc(对照) − bpc(实验)，**正 = MoE 更好**）：

   | 判据 | s0 | s1 | 落点 |
   |---|---|---|---|
   | ① 主判 E4（等激活 MACs） | **−0.01057**（带内） | **−0.00186**（带内） | 两 seed 都落带内 ⇒ **不可排序（买不到质量）** |
   | ① 主判 E8（等激活 MACs） | **−0.02280**（越负带 1.63×） | **−0.01315**（带内） | 未同时越带 ⇒ **本 n 下不可排序** |
   | ② 专家数（E4 − E8） | **−0.01223**（带内） | **−0.01128**（带内） | 两 seed 都落带内 ⇒ **专家数买不到质量** |
   | ③ 等参数旁证（旁证，不参与主判） | **−0.01806**（越负带 1.29×） | **−0.01673**（越负带 1.20×） | 两 seed 同向越带 ⇒ **MoE 劣于同参数稠密** |

   参数限定必须与判词同段读：`dense-B0` 13.6M（token/param 7.227）、`moe-top1-E4` 42.0M（3.087×，2.341）、
   `moe-top1-E8` 79.8M（5.869×，1.231）⇒ **E8 臂的欠拟合风险最大**，所以 E8 的负读数**不能**读成「专家越多越差」。
   代价侧：每 token 专家 MACs 与 dense 的比值**恰为 1.000000**（路由税 +0.13% / +0.26%），峰值显存 2992 → 3931 /
   4646 MiB（1.31× / 1.55×），墙钟 4.03 → 8.24 / 12.66 min（申报列，不进判词）。
6. **结论与下一步**：见下面三句与 §7。

**三句结论**：

1. **同激活算力下，本尺度买不到质量**：E4 两 seed 都落带内（−0.01057 / −0.00186），E8 一个越负带一个落带内
   （−0.02280 / −0.01315）⇒ 按预登记判「不可排序」，**不写「MoE 无效」**，只写「13M / 98.3M token 这个预算下买不到」。
2. **专家数这条轴（E4 → E8）在本尺度没有正收益**：两 seed 都落带内（−0.01223 / −0.01128），方向都是负的（t = −7.79 / −5.40），
   而参数从 42.0M 涨到 79.8M、token/param 从 2.34 掉到 1.23 ⇒ **「容量买不到」和「容量买到了但欠拟合」这两条解释在本 n 下分不开**。
3. **旁证把「是不是纯容量」这一问答掉了（且方向对 MoE 不利）**：`dense-eqparam-E4`（同 42.0M 参数、每 token 4× 算力）
   比 `moe-top1-E4` 好 **−0.01806 / −0.01673**（两 seed 同向、越负带）⇒ **MoE 的稀疏与路由没有独立贡献**；这两臂参数量
   相等而算力不等，所以它**只作旁证、不参与主判**（`README.md` §2、`harness/SCHEMA.md` §15）。

## 1 它是干什么的 / 改了什么叫 / 怎么测的（六问 1–4 的详细版）

**它要回答什么（六问 1）**：同样的**每 token 激活算力**下，把每层 FFN 拆成 E 个「只有一部分被用上」的
专家，能不能比同算力的稠密基线买到质量。这一问只有在**同激活算力**下才有意义——同总参数比，MoE 必然赢
（参数多），那不说明它值。

**相对普通 decoder-only 改了什么（六问 2）**：只改 FFN。每层 `Block.mlp` 换成「E 个同宽专家
（`h_e=1536`，与 stock 的 `mlp_mult=6` 同宽）+ 一个 `d×E` 路由器」，每 token 只过 top-1；top-1 的权重
归一到 1.0（不归一时权重是 `p_max<1`，等于把 FFN 输出整体缩小，是第二个混杂）。注意力 / LN /
embedding / 读出 / 层数 / 残差接线一字未改；同 seed 下 MoE 臂的非 FFN 参数从 stock dense 臂**逐位拷贝**
（`copy_shared_from`），所以臂间唯一差异是 FFN。路由器**没有**负载均衡辅助损失（均衡属 `4.2`）。

**为什么要改（六问 3）**：稠密 FFN 把「容量（参数量）」与「每 token 计算量」绑死。MoE 的卖点是把这个
绑解开：参数 ×E，激活算力不变。本格要判的就是**这笔容量能不能兑现**，以及代价（参数、路由税、路由行为）
是多少。

**怎么测的（六问 4）**：13M 基底（`d=256 / L=12 / H=8`）、enwik8 字符级、**6000 步 × batch 32 × seq 512
= 98,304,000 token/臂**（= `configs/B0.json` 的同一预算）、seed 0 与 1；20 批 × bs16 的**配对**
clean bpc（末 10M 留出、fp32、无 autocast、同 `window_seed` ⇒ 全臂逐批同窗）。判据线在跑之前写死并用
`tools/prereg_bind.py` 绑定（最终 `bound_at` 见 `prereg_binding.json`，六次重绑的逐条理由见 §3 与
`README.md` §10）⇒ 判据「先绑后用」。

### 4.1 判词（按预登记规则逐条，`results.json::main_verdict` / `::criteria`）

- **① 主判（等激活算力）**：`E4` **两 seed 都落 0.014 带内**（−0.01057 / −0.00186）⇒ **同激活算力下不可排序
  （买不到质量）**；`E8` s0 越负带（−0.02280，1.63× 带）而 s1 落带内（−0.01315，0.94× 带）⇒ 按 `verdict_rules`
  的「同向但未同时越带」分支判 **本 n 下不可排序**，不解释成噪声、不取平均掩盖。**两 seed 的方向都是负的**
  （E4 的 t = −5.71 / −1.71，E8 的 t = −11.34 / −6.84，Δ>0 的批占比 0.0–0.4）——这一点与「不可排序」一起读：
  数据不支持「MoE 更好」，也没有在两 seed 上同时证到「MoE 更差」。
- **② 专家数（E4 → E8，低端两点）**：**−0.01223 / −0.01128**，两 seed 同向（都是负）但都落带内 ⇒
  **专家数买不到质量**。这条轴只有 **E4 / E8 两个点、参数 1.9×**，而且两点都在**低端**：结论**不外推**到
  「更多专家更值」或「大 E 不行」。
- **③ 归因（`dense-eqparam-E4` 旁证，不参与主判）**：**−0.01806 / −0.01673**，两 seed 同向、各自越负带
  1.29× / 1.20× ⇒ **MoE 劣于同参数稠密**，「稀疏/路由本身有贡献」这条被否掉。读法限定：该臂参数量相等
  （41,969,152 vs 41,990,656，相对差 0.051%）而**每 token 激活算力是 MoE 臂的 4 倍**（37,748,736 vs 9,449,472 MACs），
  所以它只回答「MoE 的差异是不是纯容量」，**不是**等算力对照、**不进主判**。
- **④ 代价（申报，不进判词）**：专家 MACs 比值恰 `1.0`（`c4_cost::expert_macs_equal_all_main_arms = true`），
  路由税 +0.13% / +0.26%，峰值显存与墙钟见 §6。
- **⑤ 必须不变（实现恒等点）**：`E=1, top-1` 灌入 stock `mlp` 权重后与 dense 逐位相等（`preflight.json`
  `bitwise_equal = true`；回归见 `test_moe_forward_equivalence.py`），参数量解析式 == 实测。
- **⑥ 路由行为**：四条 MoE 臂**都命中坍缩登记**（详见 §5）。
- **⑦ 入场门**：8/8 过（`gnorm_max` 3.87–18.66，`grad_skips` 全 0）。

## 7 失败归因与边界

按 `harness/SCHEMA.md` 的三分法（物理不可能 / 我们的方法有问题 / 实现有问题）逐条排除：

1. **实现问题：排除。** ① `E=1, top-1` 灌入 stock `mlp` 权重与 dense **逐位相等**（`preflight.json` +
   `test_moe_forward_equivalence.py`，含反恒真断言）；② 分组前向与朴素前向 `max_abs_diff == 0`（同权重同输入）；
   ③ 8/8 臂过入场门（`gnorm_max` 3.87–18.66、`grad_skips` 0）；④ 专家 MACs 比值**恰 1.000000**（记账自洽）；
   ⑤ 同 seed 下 MoE 臂的非 FFN 参数从 dense 臂**逐位拷贝**（`copy_shared_from`），臂间唯一差异是 FFN；
   ⑥ 路由确实在训练（使用率分布随层显著偏离均匀，见 §5）。**唯一实现层面的披露**是本轮修掉的三处汇总缺陷
   （§3），三处都在 eval 段、不碰训练，且判词方向在「预演 vs 正式」两版代码上一致（§4.3）。
2. **我们的方法有问题：部分可能，已量化。** 本格的两个已知可能都是**设计边界**而不是错误：
   ① **无负载均衡辅助损失**（`aux_weight = 0`，单因素：均衡属 `4.2`）⇒ 浅层路由集中（§5），没有被任何机制纠正；
   ② **token/param 只有 2.34 / 1.23**（dense 7.23）⇒ E8 臂的欠拟合风险最大。这两条都不能用本格的读数分开：
   它们在 E4 与 E8 上是同时变化的。**能分开的那一半由旁证给了**：等参数稠密（42.0M，4× 算力）比 MoE-E4 好 0.018
   ⇒ 「多给了参数但每 token 走狭窄路径」这件事本身不产生收益，不是纯粹「欠拟合」。
3. **物理上不可能：不成立，也不该这么说。** 本格只测了 13M 基底、98.3M token、E∈{4,8}、k=1、无均衡、单卡、enwik8
   字符级。**在这个尺度上，业界结论（MoE 在大 token 预算下赢）无法被检验**，所以本格的结论只能写成
   「**13M / 98.3M token / 无均衡 / 低端两点**这个预算下，等激活算力的 MoE 买不到可测质量」，**不得**外推成
   「MoE 无效」或「专家数无用」。

**边界（逐条）**：

- **尺寸**：13M 基底（`d=256 / L=12`）。SCHEMA §7 的规模纪律：本尺度上专家数少、容量与算力的解耦幅度小。
- **专家数**：只有 E4 / E8 两点（参数 1.9×），**都在低端**；不外推到 E16+ 或细粒度专家。
- **token 预算**：98.3M（1.1 epoch of enwik8-90M）。MoE 的常规做法是**大得多的 token 预算**；token/param 1.23 是
  「容量买到但没喂饱」的典型区间，本 n 下分不开。
- **路由**：top-1、权重归一、`aux_weight = 0`、无 router z-loss、无 capacity factor ⇒ 结论是关于「朴素 top-1」的，
  不是关于「带均衡的 MoE」。
- **数据/分词**：enwik8 字符级（vocab 206），clean bpc 口径；不外推到 BPE / 真词表 / 下游任务。
- **判据**：clean bpc 越 0.014 带才算可排序；「不可排序」是本 n 下的读法，不是「差值为零」的证明。

**下一步最小实验（都不属本行，登记在 `project.yaml::gaps`）**：

- 把 `4.2` 的负载均衡项（Switch 式 `aux` 或 aux-loss-free bias）叠到同一对臂上 ⇒ 判「浅层坍缩是不是质量上不去的
  原因」，需新契约（4 臂 ≈ 35 min GPU）。
- 把 token 预算抬到 token/param ≈ 7（E8 臂要 ≈ 560M token）⇒ 判「容量买到但没喂饱」，单臂 ≈ 75 min GPU。
- 等算力的 `dense-eqparam` 对照（同 9.44M MACs 的稠密）已经由本格的 `dense-B0` 承担；若要拆「宽度 vs 专家数」，
  需再加「E4 但 `h_e` 减半 + k=2」一档（4.2 / 4.3 的边界）。
