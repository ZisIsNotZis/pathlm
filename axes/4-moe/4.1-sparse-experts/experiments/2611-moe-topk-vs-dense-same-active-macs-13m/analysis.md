## 1 它是干什么的 / 改了什么叫 / 怎么测的（六问 1–4 的详细版）

**它要回答什么（六问 1）**：同样的**每 token 激活算力**下，把每层 FFN 拆成 E 个「只有一部分被用上」的
专家，能不能比同算力的稠密基线买到质量。这一问只有在**同激活算力**下才有意义——同总参数比，MoE 必然赢
（参数多），那不说明它值。

**相对普通 decoder-only 改了什么（六问 2）**：只改 FFN。每层 `Block.mlp` 换成「E 个同宽专家
（`h_e=1536`，与 stock 的 `mlp_mult=6` 同宽）+ 一个 `d×E` 路由器」，每 token 只过 top-1；top-1 的权重
归一到 1.0（不归一时权重是 `p_max<1`，等于把 FFN 输出整体缩小，是第二个混杂）。注意力 / LN /
embedding / 读出 / 层数 / 残差接线一字未改；同 seed 下 MoE 臂的非 FFN 参数从 stock dense 臂**逐位拷贝**
（`copy_shared_from`），所以臂间唯一差异是 FFN。路由器**没有**负载均衡辅助损失（均衡属 `4.2`）。

**为什么要改（六问 3）**：稠密 FFN 把「容量（参数量）」与「每 token 计算量」绑死。MoE 的卖点是把这个
绑解开：参数 ×E，激活算力不变。本格要判的就是**这笔容量能不能兑现**，以及代价（参数、路由税、路由行为）
是多少。

**怎么测的（六问 4）**：13M 基底（`d=256 / L=12 / H=8`）、enwik8 字符级、**6000 步 × batch 32 × seq 512
= 98,304,000 token/臂**（= `configs/B0.json` 的同一预算）、seed 0 与 1；20 批 × bs16 的**配对**
clean bpc（末 10M 留出、fp32、无 autocast、同 `window_seed` ⇒ 全臂逐批同窗）。判据线在跑之前写死并用
`tools/prereg_bind.py` 绑定（最终 `bound_at` 见 `prereg_binding.json`，`README.md` §10 记了三次绑定的
理由）⇒ 判据「先绑后用」。

## 2 臂与记账（`ledger.json`）

| 臂 | FFN 形态 | 总参数 | ×dense | 专家 MACs/token | 路由税 | token/param |
|---|---|---|---|---|---|---|
| `dense-B0`（主对照） | stock `mlp_mult=6` | 13,602,304 | 1.000 | 9,437,184 | — | 7.227 |
| `moe-top1-E4` | 4 专家 top-1 | 41,990,656 | 3.087 | 9,437,184 | +0.13% | 2.341 |
| `moe-top1-E8` | 8 专家 top-1 | 79,837,696 | 5.870 | 9,437,184 | +0.26% | 1.231 |
| `dense-eqparam-E4`（旁证） | stock `mlp_mult=24` | 41,969,152 | 3.085 | 37,748,736（4×） | — | 2.342 |

- **等激活算力**：两个 MoE 臂的每 token 专家 MACs 与 `dense-B0` **逐位相等**（比值恰 1.000000，
  `ledger.json::checks.expert_macs_ratio_vs_dense`）；多的只是路由器 `E·d` logits。
- **等参数旁证**：`dense-eqparam-E4` 与 `moe-top1-E4` 参数相对差 0.051%（`SCHEMA.md` §15 的归因对照），
  但它的每 token 激活算力是 4×——所以它只回答「MoE 的增益是不是纯容量」，**不参与主判**。
- **参数记账作为限定**：MoE 臂参数是稠密的 3.09× / 5.87×，而 token 预算固定 ⇒ MoE 臂的
  token/param 只有 2.34 / 1.23（稠密 7.23）。这是本判决的第一顺位解释候选，必须与判词同段读。

## 3 判据线（预登记，跑后不改）

| # | 判据 | 线 | 方向 |
|---|---|---|---|
| ① 主判（等激活算力） | Δ = bpc(`dense-B0`) − bpc(`moe-top1-E{4,8}`) | 0.014 配对带；两 seed 同向且都越带才入词 | Δ>0 = MoE 买到质量 |
| ② 专家数（低端两点） | Δ = bpc(E4) − bpc(E8) | 同一条带 | Δ>0 = 专家更多更好 |
| ③ 归因（等参数旁证） | Δ = bpc(`dense-eqparam-E4`) − bpc(`moe-top1-E4`) | 带内 ⇒ 质量差异由参数容量解释 | Δ>0 = 稀疏本身有贡献 |
| ④ 代价（申报） | 每 token MACs、峰值显存、墙钟、token/param | 专家 MACs 比值必须恰 1.0 | 不进判词 |
| ⑤ 必须不变 | E=1/top-1 灌 stock 权重 ⇒ 与 dense 逐位相等；参数量解析式 == 实测 | `preflight.json` + 测试 | 不等即中止 |
| ⑥ 路由行为 | 逐层归一化熵 / 最大专家占比（评测期 20 批累计） | 坍缩登记线：熵 <0.5 或最大占比 >0.5 | 必须报 |
| ⑦ 入场门 | `gnorm_max < 100` 且 `grad_skips == 0` | 破门该臂作废 | — |

**换实现、换专家数第二点的披露**：`README.md` §10 写全了三次绑定的理由（旧实现 0.40 s/step → 分组前向
0.2075 → 专家数第二点 E=16 → E=8）。三次都**没有动**判据线、0.014 带、种子、评测口径、token 预算与步数。

**第四次到第六次重绑（本文件记，`README.md` §10 有逐条披露）**：

- 第四次（`2026-10-21T17:38:50+08:00`）：`eval` 的 Δ 对账写成「舍入后的 Δ vs 未舍入的均值差」再卡 2e-6，
  5 位小数的舍入误差本身可达 5e-6 ⇒ 正确读数会报假红。改成「报出的 Δ vs 两端报出的 bpc 均值之差」。
- 第五次（`2026-10-21T17:44:31+08:00`）：`eval` 段仍写着 E=16 时代的
  `led["checks"]["router_tax_e16_pct"]`，而 `ledger()` 只产出 `router_tax_e4_pct` / `router_tax_e8_pct`
  ⇒ 8 臂训完、`--stage eval` 必在构造 `c4_cost` 时 `KeyError`。改这一个**申报列**的键名；补
  `test_eval_ledger_keys.py` 把「`eval` 取用的键必须真在 `ledger()` 的产出里」变成机检。代价：第四次绑定下
  已训完的 `runs/dense-B0-s0`（6000 步、4.08 min、峰值 2992.3 MiB、`gnorm_max` 9.88、`grad_skips` 0、
  13,602,304 参数）按元级裁决停跑，整轮 8 臂重训。
- 第六次（`2026-10-21T18:59:24+08:00`，**当前生效**）：第五次绑定下跑完的 8 臂（全部 exit 0、8/8 过稳定性门、
  训练合计 63.5 min）交回后，`--stage eval` **连撞三处**——① `accumulate_usage` 把 CUDA 上的 `last_usage`
  加进 CPU 的 float64 累加器（`RuntimeError: Expected all tensors to be on the same device`）；
  ② 自洽门容差 2e-6 与 5 位小数的落盘口径不兼容（正确读数实测 1.0e-05，被判死）；③ 收尾 print 对 `crit`
  整体取 `v["verdict"]`，而主判只有 `E4`/`E8` 两档 ⇒ `KeyError`（晚于 `write_results`）。三处一次修完再重绑：
  ①`.cpu()` + 累加器显式建在 CPU 上，②按舍入误差推出 1.5e-05（推导见 `README.md` §4「自洽门」），
  ③抽成纯函数 `crit_verdicts()`；回归测试为 `test_eval_ledger_keys.py` 与
  `test_eval_routing_accumulate.py`。代价：第五次绑定下的 8 臂读数作废、第三次重训。
- 六次重绑共同的口径：**判据线（①–⑦）、0.014 带、臂清单、配对规则、评测口径、token 预算、步数、
  种子一字未动**；动的只是 harness 侧的接线、自洽门与披露文字。当前 `runs/` 与实验根 `results.json`
  全部由第六次绑定的 `run.py`（sha256 `7cf7c702…f9ddc0c`）产出，且产物时间晚于 `bound_at`。
