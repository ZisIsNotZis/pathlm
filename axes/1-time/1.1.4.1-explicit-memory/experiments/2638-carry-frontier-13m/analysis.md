## 0. 人话摘要

**我们干了什么**：给 13M 的小模型一条「显式记忆」通道——模型可以主动把看过的内容写进一个
**固定大小的小本子**（8192 个数，与序列长度无关），然后按当前问题读出来。问题不是「它有没有被用到」，
而是出资人真正要的那句：**这笔账值不值**——把「每位置占多少内存」放在横轴、「损失（bpc，越低越好）」
放在纵轴，看这条通道能不能把曲线往「全量注意力」（100% 质量）那一边推。

**结果（一句话）**：不值——**它买不到一个窗口位置的等效上下文，而且花的钱还更多**。

**为什么这么说**：普通注意力只看最近 16 个位置时，bpc = 1.6281（越低越好）；加一个小本子后
变成 1.6250（只降 0.0031，等于把「窗口 16 → 全量」这段差距补了 **2.5%**）。
而**只要把窗口从 16 直接加宽到 17**（多存 1 个位置，内存 208,896 字节），bpc 就到 **1.6241**——
**比小本子的 1.6250 还好，而且占的内存更少**（208,896 < 小本子的 212,992）。
换句话说：小本子（含它自己的 16 位置窗口）总共相当于 17.33 个位置的内存，但质量只等于「窗口 16.9」，
而「窗口 17」用更少的内存就打赢了它。**它与全量注意力之间的差距（1.5027）几乎没有被拉近**：
把窗口直接开到 128，差距就补了 91.5%；开小本子只补 2.5%。

**参照系（人话量级）**：窗口 16 → 全量，bpc 差 0.1254（这就是「丢掉长上下文」的全部代价）。

| 做法 | 每位置等效内存（k_eff，等效窗口位置数） | bpc（越低越好） | 补回了多少差距 |
|---|---|---|---|
| 窗口 16（无小本子） | 16.00 | 1.6281 | 0% |
| **加小本子（显式状态）** | **17.33** | **1.6250** | **2.5%** |
| 窗口 17（只加宽 1 格） | 17.00 | 1.6241 | 3.2% |
| 窗口 18 | 18.00 | 1.6200 | 6.5% |
| 窗口 24 | 24.00 | 1.5999 | 22.5% |
| 窗口 128 | 128.00 | 1.5133 | 91.5% |
| 全量注意力（stock 全因果） | 256.00 | 1.5027 | 100% |

**结论**：在本实现（**单共享槽**、delta 写、线性读、只从输入流写）、本尺度（13M / 12k 步 / 真实文本
enwik8）下，「显式状态在同等内存下改善质量-代价前沿」**被否证**——它被一个只宽 1 个位置的纯窗口
**严格支配**（内存更少、质量更好；点估计支配；σ_cell 读法下为边缘、0.014 带读法下不显著，见 §3）。
这**不是**说 delta 规则族不可能；§5 的失败归因把主因归到
**实现/设计退化**（55-review M-05/M-06 已指出：引擎开销把逐层状态逼成了单共享槽），
完整机制（逐层状态 + 门控衰减 + 内容相关写入门）未测，见 §7 未测项。

## 2. 前沿与支配关系（`results.json.frontier`）

- 按总字节排序的**下包络（lower envelope）** = `[win16, win17, win18, win24, win32, win128, full]`
  ——**全部是纯窗口点，carry16 不在包络上**。
- **支配关系**：`carry16_s0` 被 `win17_s0` 支配；`carry16_s1` 被 `win17_s0`、`carry16_s0` 支配。
  - 支配的定义（两轴皆越小越好）：`总字节 ≤ 212,992 且 bpc < 1.624979`。
    `win17_s0`：208,896 B（更少）且 bpc 1.624104（更好 0.000875）⇒ **严格支配**。
- 同 k_eff=17.33 的纯窗口插值点（在 win17 与 win18 之间）= **1.62272**，
  比 carry16_s0 **好 0.002259**、比 carry16_s1 好 0.003920。
- **不依赖追加臂的独立加固（B3）**：只用**预登记点集**（win16 1.628110 → win24 1.599856 的弦）
  插值到 `k_eff=17.3333` ⇒ 1.628110 + (1.3333/8)×(−0.028254) = **1.623401 > 1.624979**（差 −0.001578）
  ⇒ 「carry 不占优」**不依赖事后追加的 win17/win18**，追加臂不构成选择性偏差。

## 3. 噪声带（双列，口径归因不自选）

- **本格自测 σ_cell**（同配置换种子极差，2 样本 ⇒ 描述量）：`win16` = **0.000983**、
  `carry16` = **0.001661**。
- **项目 0.014 跨 run bpc 带宽**（`harness/methodology.md:19`）。
- **两种读法**：
  - 按 **σ_cell**：win17 支配 carry16_s0 的 0.000875 落在一个 σ_cell 内（**边缘**）；
    但插值差 0.002259 超过 σ_cell(0.00166)，win18 对 carry16_s0 的差 **0.005026** 远超 σ_cell ⇒ 「前沿上不占优」成立。
  - 按 **0.014**：win17 与 carry16 的差（0.000875 / 0.002259 / 0.003920）**均不越带** ⇒ 「支配」不显著。
  - **状态精度脚注（N3）**：横轴把 carry 状态按 **fp16（2 B/元素）** 计；引擎内部一律升 fp32
    （`_carry_cast`）。若按 fp32 记，`k_eff = 18.67`、同预算纯窗口插值点更低 ⇒ **carry 更差约 0.0073**
    ⇒ 方向不变、结论更强。
  - **两种读法都指向同一个决策**：显式状态的收益 ≤ 1 个窗口位置，而它自己花掉 1.33 个位置的内存
    ⇒ **不论用哪个带，它都不是一条高效的信息右移路径**（区别只在「被严格支配」还是「与 win17
    打平但更贵」）。

## 4. 分量分解与替代解释

**干预活性（SCHEMA §10）**：`results.json.liveness` 逐臂落活性块——窗口臂给掩码可见对数/`alive`
（win17: 4216/32896、`alive=true`）与训练日志 `window_mask`；carry 臂引 2634 的训练侧 `carry_liveness`
（`read_share` 0.416、β 非零、状态非零、`rel_dev_vs_channel_off>0`）；另附**评测期反事实**
`window_mask_probe(win17)` 的 `max_abs_logit_diff_masked_vs_open > 0`（掩码真的改了前向，不是死掩码）。

- **gap-closing**：carry16_s0 补回 2.5%（=0.003131/0.125421）、carry16_s1 补回 1.2%。
  窗口直接加宽的补回率：+1 格 3.2%、+2 格 6.5%、+8 格 22.5%、+112 格 91.5%。
  ⇒ **小本子的全部收益 < 加宽 1 格窗口的收益**。
- **替代解释 1「小本子没被用」**：排除。2634 的活性量（`read_share=0.416`、β 非零、状态非零、
  `rel_dev_vs_channel_off>0`）与毁源探针 `Δbpc_far = +0.0158/+0.0141 > 0` 都成立 ⇒ 状态确实被读、
  确实携带窗外信息（判据④）。
- **替代解释 2「口径不同致假优势」**：排除。全部臂同一 96×16 窗口序（window_seed=2）、
  同 token 预算（98.3M）、同数据；掩码可见对数逐臂断言等于声明值。
- **替代解释 3「真实文本局部先验太强，量不出机制」**（SCHEMA §19）：**部分成立且已记账**。
  enwik8 的局部先验把窗口 16 与全量之间的差距压到 0.1254 bpc；但**差距本身不为零**，
  且**同一判据下窗口加宽量得出清晰的前沿** ⇒ 「该任务上没有区分力」不成立；
  真正的限制是「显式状态的边际收益极小」，按 §19 只读作「该尺度/该实现不划算」。

## 5. 失败归因（顶层 `failure_analysis` 的依据）

判据③ 触发研究项预登记的否证条件 #2（「该通道点被同预算窗口/量化点支配（前沿上不占优）」）：

1. **设计/实现问题（主因）**：本次测的显式状态是**单共享槽**（`shared_slots=true`，8192 floats
   覆盖全部 12 层、只从输入流 h0 写、无门控衰减、无内容相关写入门）——正是 `55-review`
   M-05/M-06 指出的、被引擎/墙钟开销逼出的退化实现。业界主流是**逐层**状态 + 门控 + delta
   （Gated DeltaNet / GLA）；把一个 8192 数的全局槽当整模型的记忆，容量与表达力都远低于
   同量级实现。证据：状态只在「等价 1.33 个窗口位置」的内存下产出 0.0031 bpc。
2. **结构问题（次因）**：固定 8192-float 状态在 13M / 12k 步快照下的容量与收敛度是否足够，
   未与「窗口 K」做同参数量对照（carry 臂多 264,296 参数 = +1.95%）；本实验的对照是
   **同 token 预算/同窗口**，不是同参数量 ⇒ 不能把全部差异归给「容量」。
3. **非 innovation 本身失败**：本实验**没有**测完整 delta 族机制（逐层、门控、内容相关写入门），
   **不得**据此判「delta/线性状态不可能」。本项 `status = 被否证` 只覆盖
   「本实现（单共享槽）在质量-代价前沿上不占优」这一条。

## 7. 未测项与下一步最小实验 + 成本（§23 七问第 6 条）

1. **完整机制（WP2）**：逐层状态 + 门控衰减 γS + 内容相关写入门（Gated DeltaNet 式）——
   需要**改共享引擎**（`pathlm/depth_ar.py` 的 `CarryChannel` 目前是单共享槽）。
   **本轴不擅自改共享引擎**，已上报 Main（见 `.scratch/62-axis1-time/TICKET.md` §4 F5）。
   最小实验：13M、窗口 16、{单槽, 逐层槽} × 2 seed，同 96×16 口径；成本 ≈ 4 臂 × 9 min GPU。
2. **同参数量对照**：把 carry 臂的 264,296 参数换成等参数的纯窗口/等参数对照，排除「容量归因」。
3. **量化点同图（M-12）**：把 R1 的 KV 量化点（int8/int4）放到同一 (每位置字节, bpc) 图上，
   给完整的「预算点」前沿。本实验只放了窗口点与 full 锚。
4. **第二规模点/更长训练**：12k → 24k 步（验证增益是否只是快照/收敛加速，SCHEMA §16）。
5. **合成任务复核（SCHEMA §19）**：在 `assoc-mqar` 上做同预算前沿（真实文本 + 合成两组并报）。
6. **业界实现对齐**：本仓无检索、无外部代码，真实 DeltaNet/GLA 对照未做（已在 `gaps` 记录）。
