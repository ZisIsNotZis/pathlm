# 2680 · 把 KV 量化的 int8 档叠到「每位置部署字节 vs clean bpc」图上：显式状态还占优吗？

## 0 人话摘要（先看这里）

**问题。** 这一格已经量到：显式状态（`carrypl16_s0`）在 **393,216 B/位置** 处 clean bpc = **1.527595**，
而同字节的纯窗臂 `win32_s0` 是 1.595823 ⇒ 同字节上占优 0.068。但那张前沿只有 **fp16** 一档：`5.1` 早就判定
8 位 KV 量化近无损、每位置字节砍一半以上。**纯窗族可以花一半的字节买同样的窗口**，所以「同字节占优」
这张价签必须重新读。

**做法。** 对 `2634`/`2638` 已经训好的 7 条纯窗臂，只在**评测期**把 K/V 换成 int8 + 块标尺（G=32，0 训练 token），
把新点与 `2639` 落盘的 fp16 点放上同一条横轴，重算支配关系。

**结果。**

1. **量化在纯窗族自己的 checkpoint 上近无损**：7 条臂的 clean bpc 只涨 **+0.000015 ~ +0.000071**
   （`win32_s0` 为 **+0.000049**），全部远小于 0.014 带 ⇒ **本尺度无质量增量**；字节砍到 **0.53125 倍**（精确）。
2. **纯窗前沿整体左移**：`win32@int8` 在 **208,896 B** 就复现了 `win32@fp16` 在 **393,216 B** 的 bpc
   （1.595857 vs 1.595823，差在噪声里）——**一半字节买同一个模型**。
3. **显式状态仍不被支配**：`carrypl16_s0`（393,216 B、1.527595）在加入量化点后仍在低包络上；比它字节不多、
   bpc 最好的点是同字节的 `carrypl16d_s0`（1.585531），差 **0.057936**（> 0.014 带）；比它**更省字节**的点里
   最好的是 `win32@int8`（208,896 B、1.595857），差 **0.068262**。
4. **但「同字节平手」这一格不在盘上**：纯窗族要到 int8 下 **k≈60（391,680 B）** 才能到 carry 的字节水平，
   而那一条臂不存在 ⇒ 只能报「本网格上不被支配」，不能报「同字节仍占优」。

**怎么读。** 显式状态这 0.068 的同字节优势里，有一部分其实是「纯窗族当时没有便宜档」造成的：加上量化档后，
纯窗族的每位置字节减半、前沿左移，carry 点要在 **≈391,680 B** 处打赢一个还不存在的 int8 纯窗臂才算赢。
本实验把这个判据从「已占优」压成「一个可执行的最小实验」：训 1 条 `win64` 纯窗臂（12k 步 ≈10 min GPU）
+ int8 评测 ≈2 min。

## 1 判据逐条（判据线预登记在同目录 `README.md` §4，常数在 `config.json::criterion`）

| # | 判据 | 结果 |
|---|---|---|
| ① | 复现门：11 个 fp16 格与 `2639::rows[*].bpc` 逐位相等 | **过**（11/11 `equal: true`） |

| ③ | 质量腿：逐臂 `Δ_int8` 与 0.014 带比 | **本尺度无质量增量**：7 条臂 +0.000015 ~ +0.000071，全部 `< 0.014` |
| ④ | 主判（支配）：存在更少字节且 bpc 低出一个带的点 ⇒ carry 被支配 | **不被支配**：`carry_dominated: false`；对比更强的点是同字节的 `carrypl16d_s0`，差 0.057936 |

**两条必须一起报的限制（跑之前写死，见 `README.md` §2）**

1. `carry` 臂的块类不是 stock `Block`（`CarryChannelBlock`），`2632` 的量化前向只认 stock `Block`/`GQABlock`
   ⇒ **carry 族的 int8 档本轮没测**。所以这一版给纯窗族的是它自己最省的档、给 carry 族的是 fp16 ⇒ 方向对 carry
   **不利**；它仍不被支配，因此该方向稳健。
2. `carrypl16_s0` 比纯窗臂多 **264,296 参数（+1.95%）**（`2639` 已登记）⇒ 同字节优势里含参数混杂，不读成「纯机制」。

## 3 量级怎么读（本格的判读义务）

- 纯窗族：**每位置字节砍 46.875%，clean bpc 只付出 0.000015–0.000071**（≈ 「窗口 16 → 全因果」缺口 0.125421
  的 0.01%–0.06%）⇒ 量化是这张图上**最便宜的字节档**，比「把窗口从 16 加到 32」便宜得多（后者要多 100% 字节）。
- 显式状态：在 393,216 B 处比同字节的 fp16 纯窗好 **0.068**,比**更省**字节的最好纯窗点（208,896 B）好 **0.068262**,
  比同字节的退化版（γ=0.99）好 **0.057936** ⇒ 优势都越过 0.014 带，但都在**同一个 checkpoint 家族内部**成立。
- 缺的那一格：纯窗族要 **约 391,680 B**（int8 下 k≈60）才能与 carry 同字节，此点不在盘上 ⇒ 「同字节仍占优」
  **本实验不能判**，只能判「本网格上不被支配」。

## 4 未测项与下一步（各自的最小实验与成本）

1. **决定性那一格**：训 1 条 `win64` 纯窗臂（12k 步 ≈10 min GPU，配方与 `2638` 的窗口臂逐字段相同）+ 本目录的
   int8 评测（≈2 min）⇒ 391,680 B 量级的同字节对撞，才能把「不被支配」升级成「同字节占优 / 被追平」。
2. **carry 族的 int8 档**：要给 `CarryChannelBlock` 写一条量化前向（新代码 > 1 个开关），属另一档工作；
   不测它的后果是本图对 carry 偏保守（见 §2 限制 1）。
3. **第二 seed**：`win32_s0` / `win24_s0` / `win128_s0` 都只有 seed 0 ⇒ 前沿读数标**临时**；`win16` 与 `carry16`
   的两 seed 只够支撑「量化近无损」这一半。
4. **与业界实现的同字节对撞**（真实 DeltaNet/GLA）本仓仍无外部代码，未测。
