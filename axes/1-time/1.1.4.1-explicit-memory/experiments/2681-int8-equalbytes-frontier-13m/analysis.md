# 2681 判读 · int8 档下补 k=60 / k=64，看显式状态点是否被同字节纯窗口支配

## 0 人话摘要（先人话，数据在后）

**原本要回答什么**：上一轮（`2680`）把 KV 的 int8 量化档叠到「每位置部署字节 vs clean bpc」图上后，
显式状态点（显式记忆槽 + 逐层独立状态，下面简称 **carry**）落在 393,216 B / 1.527595 bpc 上，
**没被支配**。那一轮的同字节对照是 `win32@fp16`（393,216 B / 1.595823，carry 好 **0.068228**）——
对照本身同字节，但纯窗族**在自己最省的 int8 档下**落在同一字节水平的那一格（k=60 → 391,680 B）
不在盘上（当时最贵的纯窗 int8 点只到 k=32 的 208,896 B）⇒ 上一轮只能说「本网格上不被支配」，
不能说「纯窗族用最省的档、同字节也追不上」。**这次训了两条纯窗口臂（k=60、k=64）把那一格补上。**

**实际怎样**：补上以后，结论从「本网格上不被支配」变成「**含同字节格的网格上仍然不被支配**」，
但赢的幅度比上一轮报的小了很多，这一点必须讲清楚：

- 同字节上最强的纯窗口挑战者现在是 **k=60 的 int8 档：391,680 B（比 carry 还少 1,536 B）、
  bpc 1.558523**；carry 是 **1.527595** ⇒ **carry 仍好 0.030928 bpc**。
- 把尺子换成这一格的噪声带：0.030928 = **18.6 × σ_cell**（本格自测带 0.00166）、
  **2.2 × 0.014 带**（跨格配对带）⇒ 越带、可排序，不是噪声。
- 人话量级：**纯窗口要在 int8 下追平 carry 的这 0.031 bpc，每位置字节还要再加到约 1.4 倍**。
  推导（三处都在 `results.json::frontier.points`）：近邻同精度两点 `win60_s0@int8`（391,680 B /
  1.558523）与 `win64_s0@int8`（417,792 B / 1.553875）的斜率 = 0.004648 / 26,112 B = **1.78e-7 bpc/B**
  ⇒ 追回 0.030928 需 ≈**173.7k B**，即到 565k B ≈ carry 393,216 B 的 **1.44 倍**；若改用
  `win60@int8` → `win128@int8`（835,584 B / 1.513366）的全局斜率 1.02e-7 bpc/B，则是 ≈**1.77 倍**。
  取哪一对决定 1.4 还是 1.8，两个数都只作人话量级、不构成前沿点，判据④⑤ 不用它。
- 上一轮报的 **0.068228** 对着的**就是同字节**的点（`win32@fp16` 393,216 B / 1.595823），不是便宜的点；
  便宜 184,320 B 的是 `win32@int8`（208,896 B），它与 carry 的差是 **0.068262**（下表第三行）。
  本轮同字节最强挑战者换成 **`win60@int8`（391,680 B / 1.558523）**，差 **0.030928** ⇒ 上一轮的
  0.068228 没有被推翻，是**本轮的对手变强了**（量化让纯窗族在同一字节水平上更强）。

**为什么会这样 / 排除了哪些别的解释**：int8 块标尺本身几乎不掉质量（k=60 只涨 +0.000079、
k=64 只涨 +0.000066，都远小于 0.014 带），所以「纯窗口变强」不是量化换来的运气；
它的质量来自**更大的窗口**（k=32 → 60 多花 1.87 倍字节换 0.037 bpc）。也就是说：量化让纯窗口
在同等质量下更便宜，但没有把窗口的边际收益变大——carry 的机制优势因此缩小、却没被抹掉。

**没解决的**：carry 族自己的 int8 档仍未测（`CarryChannelBlock` 不在量化前向的支持范围）⇒ 这张图
给纯窗口的是它最省的档、给 carry 的是 fp16 档，**这一不对称对 carry 不利**，所以「不被支配」在
这个方向上稳健；反过来，若给 carry 也上 int8，它的字节会降到 ~208,896 B，前沿会更往左——
那是 next work，不是本轮结论。

## 2 前沿（22 个点，13 臂 × 精度档）

下包络（`results.json::frontier.lower_envelope`，按字节升序）：

`win16_s0@int8` → `win16_s1@int8` → `win17_s0@int8` → `win18_s0@int8` → `win24_s0@int8` →
`win32_s0@int8` → `win24_s0@fp16` → **`win60_s0@int8`** → **`carrypl16_s0@fp16`** → `win128_s0@int8` → `win128_s0@fp16`

两张关键对照：

| 对照 | 字节 | bpc | 差（正 = carry 更好） | 含义 |
|---|---|---|---|---|
| carry vs int8 下 k=60（**同字节、且更便宜**） | 393,216 vs 391,680 | 1.527595 vs 1.558523 | **+0.030928** | 同字节的净优势；= 18.6 σ_cell、2.2 × 0.014 带 |
| carry vs int8 下 k=64（多花 6.25% 字节） | 393,216 vs 417,792 | 1.527595 vs 1.553875 | **+0.026280** | 方向一致：多给纯窗口 24,576 B 仍追不上 |
| （对照）carry vs int8 下 k=32（`2680` 原读数） | 393,216 vs 208,896 | 1.527595 vs 1.595857 | +0.068262 | 但对手便宜 46.9% 字节，不是同字节 |

⇒ **「纯窗族用自己最省的档、同字节也追不上」这一半本轮才判成**，量级是 0.030928：上一轮那两个数都不在同一
性质上（0.068228 的对手是 fp16 档、0.068262 的对手便宜 46.9% 字节）。

## 3 它把什么说清楚了、没说什么

- **说清楚了**：在「int8 块标尺 + 纯窗口 + 显式状态 fp16」这张 22 点网格上，显式状态点
  （393,216 B / 1.527595）**不在任何更便宜或同价的点之下**；最强的同字节挑战者差一个可排序带。
- **没说**：carry 族的 int8 档（未测，需给 `CarryChannelBlock` 写量化前向）；int4 档；T ≫ 256；
  多 seed（两臂各 1 seed ⇒ 结论标「临时」，但主判据的对照点 `win60_s0@int8` 差 18.6 σ_cell，
  种子级抖动 0.00166 解释不了 0.030928）。
- **不能说**：不能说「显式状态在任意字节水平上都占优」——k=128 的 int8 点（835,584 B / 1.513366）
  在**更多字节**上比 carry 更好，这是正常的「花钱买质量」，两者不在同一预算点，不构成支配关系。

## 5 否证面

若判据④ 出现 `dominating_points` 非空，本项主问题就要改判「显式状态在这张网格上被同预算纯窗口支配」，
并直接写进 `project.yaml::conclusion`。本轮没有发生：`dominating_points = []`，
最强同字节挑战者 `win60_s0@int8` 差 0.030928。据此 `project.yaml::conclusion` 的「量化档叠图」段
把 ④ 从「本实验不能判」改为「已判：不含支配点」。
