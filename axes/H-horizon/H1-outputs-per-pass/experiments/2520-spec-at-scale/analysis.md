# 2520-spec-at-scale · 判读

## 人话摘要

「一次前向批量验证几个草稿位」（spec，推测解码）在本项目被记成税效比最好的机制，其中一条
账本判读是「@100M 墙钟收益消失，**只剩 FLOPs 口径**」。这次独立重算发现：那条判读里的
「FLOPs 口径」用的其实是**墙钟前向时间比**，不是算力比——**符号算反了**。
正确的每 token 算力 = **`(1+γ)/(1+τ)`**（γ = 每次前向喂的草稿位数，τ = 平均接受位数；
单位 = native 逐 token 的 1 次 width-1 前向）：13M 得 **1.07–1.25**、100M 得 **1.09–1.27**，
**两处都 > 1**（多花 7–27% 算力/token）。也就是说 spec **在算力上也是亏的**，
不是「算力上划算、只有墙钟不行」。它真正买到的是**顺序前向次数变少**（2.4 token/前向），
这在小模型/启动受限时值钱（13M 墙钟 1.68–1.90×），到 100M 只剩大约 1.0–1.35×，
且本机有外部作业占用、绝对墙钟不可稳定复现。

术语：**bpc**（每字符比特数，越低越好）；**tok/forward**（每次前向平均产出多少 token）；
**接受级联 a₂ / a₃|a₂**（第 2 位草稿被接受的概率 / 给定第 2 位被接受时第 3 位被接受的概率）；
**γ / τ** 见上；**`c_wall`**（实测宽度 `1+γ` 前向 / width-1 前向的**墙钟**时间比，与宽度配对）。

## 1. 算力口径（主判据）

一次前向把 `1+γ` 个位置送进同一主干，产出 `1+τ` 个 token。因此

    R = 每 token 算力 = (1+γ)/(1+τ) = (1+γ) / tokens_per_forward      （native = 1.0）

- `R` 是**纯解析量**：只用到 γ（协议参数）与 tokens_per_forward（解码计数），与 GPU 负载无关。
- 解析上界：`τ < γ ⇒ R > 1`；`τ = 0 ⇒ R = 1+γ`。所有测点都落在这个区间内（脚本有断言）。
- `c_wall`（宽度 `1+γ` 前向 / width-1 前向的**墙钟**比）**不是算力**：它同时含核回退、
  启动开销、外部占用。**入库制品**里可追溯的取值：13M B3 `1.283`（`w3_vs_w1`，
  `.scratch/13-four-experiments/evidence/mtp3/spec_speed.json`）、100M INT3 `5.276`
  （`.scratch/20-spec-scale/evidence/spec_speed.json`）、100M 重跑 `2.439`
  （本目录 `results.json:micro.w3_vs_w1`）——同一架构、同一协议差 2×。
  另有**未提交的烟测观测** 1.631 / 1.738 / 2.248（无制品、不可追溯）。
  把它代入「算力」会得到随环境漂移的假结论。

## 2. 旧口径 vs 正确口径（数字对照）

旧口径把墙钟比当算力：`旧账 = c_wall / tokens_per_forward`。
正确口径：`R = (1+γ) / tokens_per_forward`。二者并报（`c_wall` 与宽度配对：γ=1 用 `w2_vs_w1`、
γ=2 用 `w3_vs_w1`，即宽度 `1+γ`）：

| 引擎 | prompt | k (=γ) | tok/fwd | τ | **R（正确算力）** | 旧账 c_wall/tokfwd | 墙钟 speedup |
|---|---|---|---|---|---|---|---|
| 13M B3 | random | 1 | 1.8779 | 0.878 | **1.065** | 0.670 | 1.42× |
| 13M B3 | random | 2 | 2.6846 | 1.685 | **1.118** | 0.478 | 1.85× |
| 13M B3 | enwik8 | 1 | 1.8433 | 0.843 | **1.085** | 0.683 | 1.42× |
| 13M B3 | enwik8 | 2 | 2.3952 | 1.395 | **1.253** | 0.536 | 1.68× |
| 100M INT3 | random | 1 | 1.8349 | 0.835 | **1.090** | 2.398 | 0.80× |
| 100M INT3 | random | 2 | 2.3669 | 1.367 | **1.268** | 2.229 | 1.15× |
| 100M INT3 | enwik8 | 1 | 1.8182 | 0.818 | **1.100** | 2.421 | 0.92× |
| 100M INT3 | enwik8 | 2 | 2.3952 | 1.395 | **1.253** | 2.203 | 1.22× |

（13M 有两次独立运行（原始 + `.scratch/13-four-experiments/evidence/mtp3/spec_speed_independent_repro.json`）：
R 逐值相同，墙钟 ±3%；100M 为 `.scratch/20-spec-scale/evidence` 原始值；
原始 raw 见 `ledger.json` 与 §3 的重跑。）

**读法（这是本格算力账的当前结论）**：

1. **R 恒 > 1：spec 是算力亏损**（+7% ~ +27%/token），两个规模、两个 prompt、k=1/2 全覆盖。
   它**不随规模翻转**——enwik8 的 k=2 两点**几乎相同**（13M 1.2525 vs 100M 1.2525）；
   random 上 13M(1.118) < 100M(1.268) 的差来自**接受级联不同**（13M random 的 a₂ 更高、tok/fwd 2.68 vs 2.37），
   不是算力机制随规模变化。
2. 旧账的 **0.48→2.2** 那个「随规模翻转」是**墙钟 `c_wall` 从 1.283（13M 启动受限）涨到 5.276（100M 微基准）**
   造成的假象：13M 看起来「省算力」只是因为那次墙钟宽度比被启动开销压小，不是算力小。
3. 因此**「@100M 只剩 FLOPs 口径」不成立**：FLOPs 口径**从头到尾都是亏的**。
   100M 上真正剩下的是**微弱的墙钟收益**（k=2 约 1.0–1.35×，本机不可稳定复现，见 §3），
   以及 **forward 次数少**这一确定性事实（tokens/forward 2.37–2.40）。

## 3. 新证据（同 checkpoint 重跑）

重跑协议与 `probe_spec.py` 一致（同 prompt 长度 32、生成 400、seed 5/7/9、同进程逐次交替 plain/spec），
checkpoint = INT3_100M_s0（sha256 见 `MODEL.md`）。`run.py` 落盘 `results.json`。

**确定性量（同代码路径 / 同 checkpoint 的确定性复跑，**不是**独立复算）**：tokens/forward、接受率与
原始 `.scratch/20-spec-scale/evidence/spec_speed.json` **逐值相同**
（random_k1 1.8349 / a₂ 0.8394；random_k2 2.3669 / 0.7929 / 0.7239；
enwik8_k1 1.8182 / 0.8227；enwik8_k2 2.3952 / 0.7964 / 0.7669）。这**只证明确定性**
（同实现 + 同权重 + 同贪心 seed ⇒ 同输出），**不等于**第三方独立重算。

**接受级联 + Wilson 95% CI**（计数由 `n_rounds × 报告比例` 复原，均为整数比、可逐位核对；
CI 只描述**单个 prompt 内跨位置**的估计精度，run-to-run 方差 = 0）：

| 臂 | n_rounds | a₂（接受/总轮） | Wilson 95% | a₃\|a₂（接受/条件轮） | Wilson 95% |
|---|---|---|---|---|---|
| random_k1 | 218 | 0.8394 (183/218) | [0.7849, 0.8822] | — | — |
| random_k2 | 169 | 0.7929 (134/169) | [0.7256, 0.8472] | 0.7239 (97/134) | [0.6427, 0.7925] |
| enwik8_k1 | 220 | 0.8227 (181/220) | [0.7669, 0.8675] | — | — |
| enwik8_k2 | 167 | 0.7964 (133/167) | [0.7290, 0.8505] | 0.7669 (102/133) | [0.6882, 0.8307] |

**fp 平局（正确性腿）**：原始 run 与本次重跑**都在 enwik8_k2 记到同一次 flip**——首错位 169、
级联 68 token、翻转处 top-2 gap **0.007912**（本目录 `results.json:enwik8_k2.greedy_divergence`，
两轮逐值相同）；其余三臂（random_k1/k2、enwik8_k1）两轮均 `greedy_divergence: null`。
⇒ 该翻转处 gap **超出**预登记的 `1e-3` 并列容差 ⇒ **「spec 发出流 == 贪心」的正确性门禁在
100M enwik8_k2 不通过**；**逐位相等不是跨规模判据**（batched SDPA 与逐位置 SDPA 的核差异
在近平局处翻转 argmax，级联 68 token）。同时，该翻转的四个参数两轮完全一致 ⇒ **这反而印证了确定性**
（确定性的复跑，非独立复算）。

**墙钟（噪声大，只报相对排序与极差）**：本次重跑 5 次重复的「按 rep 配对 speedup」：

| 臂 | 配对 speedup 5 次 | 读法 |
|---|---|---|
| random_k1 | 0.96 / 0.85 / 0.93 / 1.58 / 1.25 | 跨 1，不可排序 |
| random_k2 | 0.76 / 1.16 / 1.07 / 1.05 / 1.12 | 跨 1 |
| enwik8_k1 | 0.95 / 0.80 / 0.85 / 0.93 / 0.79 | 提示 ≤1 |
| enwik8_k2 | 1.00 / 1.06 / 1.05 / 1.21 / 1.19 | 提示 ≥1，幅度 ≤1.2 |

- 重跑期间 `nvidia-smi` 显示两个外部 `llama-server` 常驻（约 7.5–11 GB），`util` 在
  19–96% 之间摆动；同一臂的 tok/s 在 5 次重复里可差 2–3×。
  ⇒ **绝对墙钟在本机不可用**；上表只能当**相对排序的弱证据**（k=2 略 >1，k=1 可能 ≤1）。
- 重跑与原始 run 的 k=2 speedup（原始 1.15–1.22）落在同一「约 1.0–1.35」带内，方向一致。

**微基准 `c_wall` 不稳定**：入库制品三次为 `2.439`（本目录 `results.json:micro.w3_vs_w1`）、
`5.276`（`.scratch/20-spec-scale/evidence/spec_speed.json`）与 13M 的 `1.283`
（`.scratch/13-four-experiments/evidence/mtp3/spec_speed.json`）——同一脚本、同一 checkpoint 跨 ≥2×。
另有**未提交的烟测观测** 1.631 / 1.738 / 2.248（**无制品、不可追溯**）。
⇒ `c_wall` 不能当算力比（见 §1），本文只把它当墙钟描述量。

## 4. 原始 `SUMMARY.md` 表内的自相矛盾

`.scratch/20-spec-scale/evidence/SUMMARY.md` 一处写「宽度-3/宽度-1 前向成本 **3.4–5.3×**」，
但同一表里的 tok/forward 与 k=2 墙钟 speedup 反解出的前向成本是

    fwd_ratio = tokens_per_forward / speedup
              = 2.3669/1.153 = 2.053（random）、2.3952/1.223 = 1.958（enwik8）   ⇒ 1.96–2.05×

两者差 2–3×，且 `3.4` 这个数**不在**原始 `spec_speed.json` 里（文件只有 `w3_vs_w1=5.276`）。
`3.4–5.3×` 是**不可核实的区间**；本次重跑进一步显示微基准自身就不稳定（§3）。
⇒ 该句应以**可核实的原始值 + 反解值并报**取代（本节给出）。

## 5. 对账（SCHEMA §12）

- **算术对账**：`R = (1+γ)/tokfwd`；解析界 `1 ≤ R ≤ 1+γ`，全部测点落在界内（脚本断言）。
  接受级联自洽：`tokfwd = 1 + a₂ + a₂·a₃|a₂`（random_k2：1+0.7929+0.7929·0.7239 = 2.367 ✓）。
- **任务对账**：native 与 spec 是**同一 checkpoint、同一 prompt、同一 `Decoder`** 上的两条解码路径；
  native 逐 token 走 `Decoder.step()`，**未**用批量 teacher-forcing 冒充。两臂都报 400 生成 token。
- **口径对账**：R（解析算力）、墙钟（同进程逐次交替）、forward 计数三者分开报；`c_wall` 只描述
  墙钟，且与宽度 `1+γ` 配对（不是把 width-3 的比值挩到 width-2 的行上）。

## 6. 未测项与成本

| 未测项 | 为什么没测 | 最小实验 + 成本 |
|---|---|---|
| 采样/T>0 下的 spec（非贪心） | 贪心下确定性最强、判据最干净 | 加 temperature=0.7 臂，重跑本脚本 ≈6–13 min |
| 树状草稿 / beam 验证 | 本引擎只有链式单行草稿 | 需引擎扩展（新 attention mask），估 1–2 h 开发 + 冒烟 |
| 更大规模（≥1B） | 单卡 4090 预算外；R 是解析量、与规模无关 | 只需一次推理即可复核 R，但需权重 |
| 与 retry/exit 的组合 | 组合默认留白（scope） | 另立组合格 |
| 真实 batch>1 部署的墙钟 | 本引擎 B=1 部署语义 | 需 batch 解码路径 |

## 7. 结论句

**spec（MTP 批量验证）买的是「顺序前向次数」（tokens/forward ≈2.4），不是算力**：
每 token 算力 `(1+γ)/(1+τ) ≈ 1.07–1.27`（13M 与 100M 都 >1，恒为亏损）。
「@100M 只剩 FLOPs 口径」应改为「**FLOPs 口径两个规模都亏；100M 上唯一剩下的是 k=2 约 1.0–1.35× 的
微弱墙钟收益，且在本机外部占用下不可稳定复现**」。
