## ① 它是什么（我的理解）
本格问「一次前向预测出的多个未来位置，该用哪条路径产生草稿」——同一个模型同时训了「直连头 `T2(h_N)` 预测 N+2」和「条件链头 `T1(chain_cat([h_N, embed(d1)]))` 以 N+1 为条件预测 N+2」，本格比较用哪个头 / 两个头按概率混合哪个做草稿更好。

## ② 对着什么 sota / 我们偏离在哪
- **sota**：DeepSeek-V3 的 MTP 用顺序条件头（本格的 `chain` 形态）；Medusa 用并行头（≈ `direct`）；Leviathan/Chen 的投机解码无损性（本格用作门禁）。**这些是本仓 `PRIOR_ART.md` §H3 自列，我无联网核证。**
- **偏离**：业界**没有**把「直连 vs 条件链」当**同一次前向上的唯一变量**对照过（本仓 PRIOR_ART 与本实验 §8.4 都这么说）——这一点是真的增量。

## ③ 五类问题逐条

### 【专项要求】实现核实 + 用户疑点（第 19 项）
**(A) 是否真的实现了三条路线？——是，我逐行核到。**
- `spec_arms.py::second_slot_logits`：`chain → nodes[1]["chain2"]["logits"]`、`direct → nodes[2]["logits"]`、`combined → λ·softmax(chain2)+(1−λ)·softmax(node2)`（λ=0.5 预登记）。`make_draft_fn` 把第 N+2 位随臂变、第 N+3 位固定为 `nodes[3]`。
- `pathlm/model.py:328-360`：`chain2 = self.transforms[0](self.chain_cat(cat([h, embed(t_next)])))`；`t_next` 在 `condition is None` 时 = `node1.logits.argmax`（`model.py:339-345`），即**真·以 N+1 为条件**。
- 单测钉住：`test_spec_arms.py:67`（chain 读 chain2）、`:96-108`（combined 是概率混合、非 logits 线性组合）、`:207`（chain2 ≠ `T1∘T1` latent 复用）；变异 `M3/M7` 抓红（`mutation_report.json`）。⇒ **不是 `T∘T` 冒充，也不是标签冒充。**

**(B) 用户疑点：「三条路线各自独立训练，为什么第 1 个草稿词的接受率不同（0.844 vs 0.657）？」**
**前提不成立——三臂不是各自独立训练，它们共用同一个 checkpoint。** 证据：
- `train_arms.sh` 的训练单元是 `<scale>_s<seed>`（`13m_s0 / 13m_s1 / 53m_s0`），**没有 arm 维度**；`run.py::load_ckpt` 对每个 ckpt 目录加载一次模型，然后 `accept_pass` 在同一模型上跑 `native + chain + direct + combined`。`config_13m.json` 里也没有任何按臂切换的训练开关。
⇒ **不存在「训练各自漂移」**：三臂只在**解码时**替换 `draft_fn`（`alternating` 同一进程、同一 prompt、同一验证器）。且门禁 `bit_identical_all_arms=True` 说明三臂**发出的 token 流逐位相同**，即验证时的参照序列完全相同 ⇒ 0.844 vs 0.657 是**纯草稿质量差**，不是分布漂移。

**那差值从哪来？——不是「第 1 个头被带坏」，是条件链头在部署时的条件输错了。**
- `model.py:454-461`：`chain2` 训练时被 `targets[:, 1:]`（**真 t_{i+1}**）条件化（teacher forcing）。
- `decode.py::decode_spec` → `Decoder.step_multi` → `model._mtp_nodes(h)`（**不传 condition**）⇒ `model.py:339` 走 deploy 分支，条件 = **模型自己 `node1` 的 argmax**。
- 该模型的下一 token 准确率只有 **0.6865（13m_s0）/ 0.6862（13m_s1）/ 0.7105（53.9m_s0）**（`results.json` `bpc.next_token_acc`，行 114/4762/9293）⇒ 约 **29–31% 的位置上这个条件 token 是错的**；`chain2` 就被推到训练分布之外，而 `direct`（`T2(h_N)`）不吃这个条件，故不受影响。
- 独立旁证（同一引擎、更早的解码口径）：`axes/H-horizon/H3-composition/experiments/2512-overnight-causal-chain/README.md` 记「oracle 链（真 t+1 条件）**0.682** ≈ node-1 0.693；deploy（自 argmax 条件）**0.547** < direct **0.560**，**~31% 草稿错误**」。⇒ 条件**正确**时链头不差（甚至更好），条件换成自己猜的就掉下来了；这正是 exposure bias 的指纹。

**「链式目标把第 1 个头带坏」这一假说：本实验无法判，且有一个未控制的真实混杂。**
- `chain2` 复用的是 **`transforms[0]` = `node1` 自己的变换头**（`model.py:358` `chain = self.transforms[0](h_c)`），所以 `chain2` 的梯度**会回灌进 `node1`**。这是真的结构耦合，但**本实验没有做任何消融**（也没有 chain-oracle 臂），所以既不能证实也不能排除「链式目标削弱了共享变换头」。
- 注意：该混杂**在同一模型内**，对三臂是同一份权重，**不可能解释臂间差**；它只会影响「这个模型自由 train-时是否已经变差」这一独立问题。

**(C) 要区分「条件错」与「头本身差」，必须补什么实验（具体、便宜）：**
1. **加 `chain-oracle` 臂**（唯一改动 = 解码时把 `d1` 换成数据里的真 `t_{N+1}`，即把 `condition` 显式传给 `_mtp_nodes`）：若 α₁ 从 0.657 → ≥0.84（≈direct），则「部署条件错」是根因；若仍低，则是头容量/训练问题。成本 ≈ 纯推理。
2. **按 `v1 == 真 t_{N+1}` 分层报 α₁**（prompt 的下一字符从 enwik8 val 直接可读，**不需要 GPU**）：若 α₁(条件对) ≈ 0.84 且 α₁(条件错) ≈ 0.2–0.3，即定量证实级联；这也能给出「α₁ 差随基座错误率缩放」的曲线。
3. **训练侧消融**（若要回答「共享头有没有被带坏」）：同配方训一个 `n_mtp=3, chain_mode="latent"`（无 token 条件链、无 `chain_cat`）的对照，比较 `next_token_acc`；若显著高于 0.6865，才说明链式目标削弱了共享头。

**其余问题：**
**2. 过程错误：有（但方法学本身是本项目最干净的一份）。**
- 该实验做对了很多：按 prompt 聚类的 bootstrap（不是把每轮当独立二项）、同进程交替墙钟、§15 不适用（三臂零新增参数）的显式论证、变异 M1–M7 全抓红 + 逐字节还原、`reconcile_report.json` 141 检查 0 失败。这些我独立看过了，成立。
- **但结论的适用面比题目窄**：因为三臂共用同一 checkpoint（且**两条头都是一起训的**），本实验回答的是「**给定一个同时训了两种头的模型，解码时该用哪个头**」，**不是**「用链式目标训练 vs 用直连目标训练，哪条路线更好」。catalog 的 H3 verdict（`catalog.yaml:678-722`）写法容易被读成后者。而且第一档（2613）已因 A6 被降级，本格现在只剩这一个实验。
- **外部占用污染墙钟**：`2631/analysis.md` §5 明说整个评测期有非本仓 `llama-server` 占满（util 77–100%），加速比被**抬高**，只能当该水位的快照。这点作者自己写清了，我会保留但必须继续说：**「1.58× 墙钟」不可引用为部署收益**。

**3. 结论错误：有（算力口径，全 axis 最严重的一条）。**
`2631/analysis.md` §2.1/§3 与 `catalog.yaml:678-722` 报「**等效算力净账 = c₃/(tok/fwd) = 0.48/0.49/0.56** ⇒ direct/combined 每 token 只需 native 的 **~48–52% 算力（≈1.9–2.1× 算力效率）**」。`spec_arms.py::micro_forward_cost` 测的是 `step_multi(3 tokens)` 与 `step(1 token)` 的**墙钟 min 比**（13.4M 得 `c₃≈1.25`）——那是 launch-bound 的墙钟，不是算力。一次宽度-3 前向要过 3 个位置 ⇒ 层-位置/线性 FLOPs ≈ 3×，头也跑 3 份 ⇒ 每 token 算力 = `3/2.58 = 1.16`（再加头 4.71% ≈ 1.22）**是亏损**，不是 0.48。
⇒ **正确结论**：本引擎 γ=2 的投机解码**在算力口径是 1.16–1.25× 的亏损**；「≈2× 算力效率」不成立，墙钟收益（且已被外部占用抬高）才是唯一真实的收益口径。作者自己在 §5 也承认 `c₃` 有 ±15% 不确定性，但没意识到它**不是**算力。

**4. 无意义：否。** 这正是用户 P-02 的核心命题，是目前全仓最该做的一格。

**5. 值得做：是（最高优先）。**
