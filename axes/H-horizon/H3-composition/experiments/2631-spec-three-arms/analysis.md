# 2631-spec-three-arms · 判读（R6 · Spec 三臂 `chain` / `direct` / `combined`）

## 0. 人话摘要（先说结论，再给数字）

**它想干什么**：让同一个模型一次前向（吃 3 个 token）、一次验证，就尽量多吐几个正确的
token，从而比「一步一个 token」的原生自回归更快。第 1 个 token 由模型自己直接出；
我们要问的是**第 2 个「投机」token（N+2）该怎么草拟**——是「先出 N+1、再拿 N+1 当条件
出 N+2」（`chain`，DeepSeek-MTP 那种条件链头），还是「从同一个状态直接出 N+2」
（`direct`，直连多 token 头），还是「把这两条分布按概率混合」（`combined`，λ=0.5）。

**测出来多少**：三个点（13.4M×2 seed、53.9M×1 seed）**一致地**给出同一个排序——
**直连头（direct）最好，概率混合（combined）和它打平，条件链（chain）明显更差**。
以 53.9M 点为例：接受长度 τ = 1.58（direct）/ 1.54（combined）/ 1.20（chain）——
「每验证一次平均多吐 0.5 个 token」 vs 「多吐 0.2 个」。墙钟加速比（vs 原生逐 token）
对应 1.58× / 1.57× / 1.39×。也就是说：**用户期待的「用 N+1 再加一」（条件链）这条路，
在这个引擎的部署口径下不赚——它比直连头少吐约 0.38 个 token/验证**；而「概率组合」
也没有跑赢「直接出 N+2」，两者在误差带内不可排序。

**为什么**：本引擎部署时，条件链的条件是**模型自己猜的 N+1**（`d1 = argmax node1`），
一旦这一步猜错，第 2 个 token 的草稿就被带偏；而直连头不吃这个级联。对照组里
`chain` 的 α₁（N+2 位接受率）只有 0.60–0.67，`direct` 有 0.80–0.84。这**复现并强化**了
ticket 12 的 deploy 结论（0.7525 vs 0.7729），并第一次给出了墙钟 CI 与算力净账。

**回答用户的核心命题（同一算力下投机解码能否更快、输出是否不变）**：
- **输出不变**：三臂的发出流与原生贪心**逐位相同**（12 prompt × 3 checkpoint 全部
  `True`）——这是比「分布保真」更强的保证（argmax 路线，见 §4）。
- **更快**：三臂的墙钟加速比 95% CI 下界**全部 > 1.0**（判定线 A 通过）。
- **哪条草稿路径最划算**：`direct ≈ combined > chain`（判定线 B：direct 与 combined
  的配对差 CI 含 0 ⇒ 不可排序；chain 显著落后）。

**没做到/存疑**：① 共享卡上全程有**外部** `llama-server` 占用（util 77–100%），墙钟加速比
**被外部占用抬高**（spec 每次前向吐更多 token ⇒ 更少排队），绝对水平只能当**该占用水位下
的快照**，不可外推到空卡；② `c3`（3 位/1 位前向成本比）有 ±15% 测量噪声；③ 只测了
γ=2、温度 0、enwik8 风格文本、53.9M 档只 1 个 seed。**禁外推**。

## 1. 命题与口径（契约 §1–§4）

| 项 | 值 |
|---|---|
| 基底 | stock `PathLM`（tied E=U、无 final LN 的宽度-MTP 解码器，`pathlm/model.py`），`n_mtp=3`、`chain_mode="token"`、`transport="none"`，其余开关全关 |
| 唯一变量（臂） | 第 N+2 草稿位的分布来源：`chain`=`T1(chain_cat([h,embed(d1)]))`；`direct`=`T2(h)`；`combined`=`argmax(0.5·softmax(chain2)+0.5·softmax(node2))` |
| 第二草稿位 N+3 | 三臂**固定** = `argmax node3(h)`（共享背景，非自变量） |
| 第一个发出位 N+1 | 不设接受测试（它就是验证器自己的输出）⇒ 投机位从 N+2 起算，γ=2 |
| 对照 | **原生逐 token 自回归**，走**同一条** `pathlm/decode.py::decode → Decoder.step()` 路径；**不用**批量 teacher-forcing 前向（`results.json::native_is_plain_decoder_path=True`，对照物是模型自身而非 oracle） |
| 训练 | 6000 步 × bs32 × T512 = 98.3M token/臂；13.4M seed{0,1}、53.9M seed{0} |
| 评测 | 贪心（温度 0）；接受率口径 12 prompt×200 token，墙钟口径 6 prompt×128 token×6 重复，同进程交替 |

**反例警示落地**：本实验的三臂**不是** `T∘T` 潜在复用。单测
`test_chain_arm_is_not_the_latent_T_composition` 钉住：`chain2`（token 条件链）与
`T1∘T1`（latent 复用，`chain_mode="latent"` 的语义）**逐元素不同**；且 `chain` 的条件项
= `d1 = argmax node1(h_N)`，是**真·以 N+1 为条件**（变异 M3 证明该接线被抓红）。
`combined` 是**概率混合**（softmax 空间），非 logits 线性组合（单测 + 变异 M7 钉住）。
⇒ **A6 要求的「以 N+1 为条件预测 N+2」与「概率混合」在本线是真实实现，不是近似冒充。**

## 2. 六项指标（逐 checkpoint × 臂；`results.json` 为原始来源）

### 2.1 指标定义

1. **逐步接受率 αᵢ（逐位置）**：`α₁ = P(a≥1)`（N+2 位）、`α₂|₁ = P(a≥2 | a≥1)`（N+3 位）。
2. **平均接受长度 τ** = 每轮平均被接受的草稿数 = `Σa / n_rounds`。
3. **tok/fwd** = 每次前向产出 token 数 = `1 + τ`（每轮发出结构恒等式）。
4. **墙钟加速比 vs native** = `spec_tok_s / native_tok_s`（同进程/硬件/批量，**交替**重复 6 次）。
5. **每 token 算力 R** = `(1+γ) / (1+τ)`，γ=2 为草稿位数、τ 为平均接受长度（相对 native 的 1.0；**越小越省，R<1 才省**）。
   **口径更正（H1 独立复核）**：**`c₃`（实测 width-3/width-1 的墙钟成本比）不是算力比**。一次宽度-(1+γ) 前向按层-位置 FLOPs ≈ `(1+γ)×` 一次逐 token 前向，故算力比是**解析量 `(1+γ)`**，与墙钟无关。旧口径 `净账 = c₃/(tok/fwd)`（得 0.48–0.60，看着像「2× 省算力」）**已撤回**，改为 `R=(1+γ)/(1+τ)`（得 1.16–1.45，**净亏**）。墙钟仅报相对排序，绝对水平受外部占用污染。
6. **分布保真**：argmax 路线 ⇒ **非分布保持**；给出更强的**逐位等价**（门禁）。

### 2.3 判定（预登记判据，契约 §4）

**门禁（逐位等价）**：三臂 × 3 checkpoint × 12 prompt，发出流与原生贪心**逐位相同**
（`results.json::bit_identical_all_arms=True`）。⇒ **输出不变，通过**。

**判定线 A（墙钟 CI 下界 > 1.0）**：**9/9** 个（臂 × checkpoint）组合通过。
即：在**本次共享卡占用水位下**，三臂都「测得墙钟收益」。

**判定线 B（臂间排序，配对差 95% CI）**：

| checkpoint | direct − combined | chain − direct | 结论 |
|---|---|---|---|
| 13.4M s0 | −0.039 [−0.089, +0.087] **含 0** | −0.113 [−0.198, −0.018] 不含 0 | direct ≈ combined > chain |
| 13.4M s1 | −0.012 [−0.093, +0.160] **含 0** | −0.167 [−0.249, −0.069] 不含 0 | direct ≈ combined > chain |
| 53.9M s0 | +0.006 [−0.007, +0.051] **含 0** | −0.165 [−0.236, −0.130] 不含 0 | direct ≈ combined > chain |

**接受率判据（Δ<0.014 不排序）**：`direct` 与 `combined` 的 α₁ 差 = 0.003 / 0.004 / −0.015
⇒ **落在不可排序带内，三者等价**；`chain` 的 α₁ 比 `direct` 低 **0.16–0.24**（远超 0.014，
且 CI 不重叠）⇒ **chain 显著更差**。

**结论**：在本引擎的**部署（argmax 条件链）口径**下，**条件链（N+1 再加一）明显不如直连
多 token 头；概率混合（λ=0.5）没有跑赢直连头**。这是一个**负结果**：它不否证「概率组合」
的一般价值（采样/树状/多级条件的组合未测），但在本实现里，把两条分布等权混合**无增益**。

## 3. 每 token 算力 R（§4.4；口径已更正为解析量）

- **口径（更正后）**：`R = (1+γ) / (1+τ)`，γ=2、τ=平均接受长度。一次宽度-3 前向按层-位置 FLOPs
  ≈ 3× 一次逐 token 前向；一轮发出 `1+τ` 个 token ⇒ 每 token 算力 = `3/(1+τ)`，以 native=1.0 为单位。
  **R<1 才省；R>1 即净亏。**
- **撤回的旧口径**：`净账 = c₃ / (tok/fwd)`（`c₃` = 实测**墙钟** width-3/width-1 比 ≈1.05–1.25，launch-bound）。
  它把**墙钟比当算力比**，给出 0.48–0.60 的「2× 效率」，是**符号级错误**（H1 独立复核）。
  已撤回的旧值：13.4M `direct` 0.51 / `combined` 0.52 / `chain` 0.60；53.9M `direct` 0.48 / `combined` 0.49 / `chain` 0.56。
- **与臂无关的草稿头成本**：每个前向都算 `T1/T2/T3`（3×d×d）+ `chain_cat`（2d×d）+
  5 个读出（5×d×V）+ 5 个 conf。按 MAC 计占主干线性 MAC 的 **4.71%（13.4M）/ 3.66%（53.9M）**
  ——四臂完全相同、臂间相消；它回答「草稿头本身有多贵」，不是臂间差异。
- **R（点估计，越小越省；`R=3/(1+τ)`）**：
  13.4M s0：`direct` **1.223** / `combined` **1.238** / `chain` **1.446**；
  13.4M s1：`direct` **1.190** / `combined` **1.207** / `chain` **1.362**；
  53.9M s0：`direct` **1.163** / `combined` **1.183** / `chain` **1.364**。
  ⇒ **所有臂 R>1，均为算力净亏**；`direct`/`combined` 亏最少（1.16–1.24×），`chain` 亏最多（1.36–1.45×）。
  **臂序不变**（direct < combined < chain）——只是量级从旧口径的「2× 省」翻成「1.2–1.45× 亏」。
  **墙钟口径另报，且只作相对排序**（绝对水平受共享卡外部占用抬高，禁外推）；**墙钟比 ≠ 算力比**。

## 4. 分布保真（§1.3-6）

- 全实验是 `temperature=0` 的 **argmax 路线** ⇒ **明确声明：非分布保持**
  （没有用拒绝采样，故输出的分布 ≠ 目标温度下的分布）。
- 本实验提供的保真是**更强的逐位等价**：发出流与同 checkpoint 的原生贪心流**逐位相同**
  （门禁，9/9）。即：投机只改变**速度口径**，不改变**输出**。
- 采样（温度 > 0）路线需要拒绝采样验证器，**未测**（记入 §7）。

## 5. 环境与测量口径（§20.2 / §20.3 的外因记账）

- **外部占用（诚实披露）**：整个评测期间共享卡上有**非本仓**的 `llama-server` 常驻 +
  外部 bench 负载，`nvidia-smi` 的 GPU util 长期 **77–100%**（读数见 `eval.runlog` 与本波
  会话）。本仓 GPU 线之间用 `/tmp/pathlm_gpu.lock` 串行，但**锁管不到外部进程**。
- **对墙钟加速比的影响（方向已判明）**：spec 每次前向吐 ~2.2–2.6 个 token、native 吐 1 个
  ⇒ 排队/切换开销对 spec 的**单位 token 成本更小**。实测：native 吞吐在占用重时 ~27 tok/s、
  轻时 ~43 tok/s，而 spec 从 ~38 到 ~63 tok/s 变化更小 ⇒ **占用越重，加速比越被抬高**。
  因此本报告给出的 **1.30–1.58× 是「本次占用水位下」的快照**，空卡上会更低；
  **禁外推**到别的硬件/负载。相对排序（direct ≈ combined > chain）在两次独立评测
  （占用重/轻）中**一致**，是可用的结论。
- **`c₃` 的测量**：`micro_forward_cost` 用**逐次交替**的单发前向、取各自最小值（避开外部占用
  的排队时间）。同一 13M 架构的多次独立测量给 `c₃ ∈ [1.05, 1.44]`（±15%），
  最干净的水位（本仓 `smoke_steptime.runlog` 与 13m_s0 评测）给 **~1.24–1.25**；
  13m_s1 那次 micro 全程被占用（`w1_min=16.9ms` vs 干净 `8.1ms`）⇒ 其 `c₃=1.05` 偏低。
  集合证据见 `evidence/micro_c3.json`（3×120 次 + 1×600 次）。**注意（口径更正）**：
  `c₃` 只用于**墙钟**讨论，**不再进算力账**；更正后的算力账 `R=(1+γ)/(1+τ)` 是**解析量**，
  不含 `c₃`，因此**其绝对水平不随 `±15%` 的 `c₃` 噪声变化**。
- **训练显存礼貌线偏离（§20.2 三件套）**：13.4M 峰值 **2972 MB**（≪5GB）；53.9M 峰值
  **6237 MB**（超礼貌线 24%），按 §20.2 优先「臂间配方一致（bs32）」并记账：逐臂
  `peak_gpu_mem_mb` 在 `train/*/results.json`；训练前后 `nvidia-smi memory.free`
  ≈16GB（余量 ≥8GB，`train_arms.runlog`）；此处显式列为偏离。

## 6. 与既有结论的关系

- **复现 ticket 12 的 deploy 结论**：ticket 12 是**批量 teacher-forcing 式**前向得出的
  「chain-deploy 0.7525 vs direct 0.7729」；本实验在**同一生产解码器**（`Decoder.step()`）
  的解码口径下得到 **chain α₁ 0.60–0.67 vs direct 0.80–0.84**——**方向一致、差距更大**，
  且补上墙钟 CI 与算力净账。⇒ ticket 12 结论的降级（原冻结清单第 8 条）
  **得到解码口径的替换结果**。
- **该格命题的正式回答**：2613 测的是 `T∘T` 潜在复用（不回答用户命题）；
  本实验测的是「以 N+1 为条件」与「概率混合」的真实现（§1 的反例警示落地）。
- **不回答**：100M 档、温度>0 的分布保真、树状候选、多级条件链（N+3 也条件化）——均未测。

## 7. 失败与未测（如实列，含成本）

| # | 未测项 | 为什么没测 | 最小实验（成本） |
|---|---|---|---|
| 1 | **多级条件链**（N+3 也以 N+2 为条件） | 引擎 `_mtp_nodes` 的 token 条件链只有**一级**（只对 node-1 产 `chain2`）；二次条件是**新结构** | 引擎新增一级条件头 + 重训（~1 GPU 小时） |
| 2 | **温度>0 的拒绝采样保分布** | 需要拒绝采样验证器（本引擎 `decode_spec` 是贪心） | 实现拒绝采样验证 + 1 次评测（~1 小时） |
| 3 | **树状候选 / 多草稿分支** | 本线只做单链 γ=2 | Medusa 式树验证改造（~半天） |
| 4 | **100M 档** | 预算（120 min）只够 53.9M 单 seed | 1×100M 训练+评测（~30 min） |
| 5 | **`combined` 的 λ 扫描** | λ=0.5 为**预登记**，事后不许调 | 属探索性，需另立工单（避免事后调参） |
| 6 | **空卡墙钟** | 共享卡全程有外部占用 | 等空卡窗口重测 `eval.sh`（~30 min） |

**实现侧的既有局限（不属本线，已在契约记录）**：`decode_spec` 的早退与投机不可组合
（批量验证须跑满深度）；`n_mtp<=2` 时 `arm_decode` 显式报错不静默退化。

| 评测 | 3 checkpoint × （接受率 12×200 + 墙钟 6×128×6 交替）≈ 27 min ×2 次（第二次为修正派生字段重跑） |
| 合计 GPU | **≈ 90 min**（契约 `gpu_wall_budget: 120 min`，未超） |

## 9. 结论一句话（可判读、可证伪）

> 在同一个 13.4M/53.9M 的 token 条件链模型上，「先出 N+1 再以 N+1 为条件出 N+2」的草稿
> 路径，其接受率与墙钟加速比**一致地、显著地**低于「从同一状态直接出 N+2」的多 token 头
> （α₁ 低 0.16–0.24；53.9M 上墙钟 1.39× vs 1.58×）；把两条分布按概率等权混合**与直连头
> 打平、不可排序**。输出在全部臂上**逐位等于原生贪心**。**绝对加速比受共享卡外部占用抬高，
> 只作该水位的快照，禁外推。**
