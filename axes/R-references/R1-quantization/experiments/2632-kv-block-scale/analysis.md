## 0. 人话摘要（先读这一段）

**这是干什么的。** 把 Transformer 推理时的 KV 缓存（注意力记忆）压成 int8 / int4 时，除了数值本身，
还要为每段数值存一把「标尺」（scale，用来把整数还原回实数）。**标尺存在哪、能摊多薄，决定量化到底
省不省内存。** 本实验只改这一件事，把 `2631` 的 27 点预算图在**块标尺（沿 head_dim 每 G 个值共用一把
标尺，G=32 为主）**下重测，并把字节账从「只算值」改成**部署字节（值 + 标尺）**。

**为什么重测。** `2631` 用**逐值标尺**（每个数值配一把 fp16 标尺）测出「int8 = 1 字节值 + 2 字节标尺
= 3 字节/值，比不压还费」，据此得出「量化在任何拓扑上都是内存负收益」。这是**与业界相反的结论**，
根因是标尺口径：业界标准是**按块/通道摊薄**（一块 32 个值共用一把标尺 ⇒ 每值只多 2/32 字节）。
审计指出本仓自己早就算过通道标尺的总开销与序列长度无关，是那次「因果化修复」把它降级成了逐值标尺。

**测出来两件事。**

1. **「8 位近无损且省约一半」这条参照线成立**——但要**换对摊薄轴**。沿 `head_dim`（块内 32 个值都是
   同一个 token 的，与 token 轴无关）摊薄标尺：int8 每位置 **6528 字节**（不压是 12288），**省 46.9%**，
   而 clean bpc 从 1.483571 只涨到 **1.483672（+0.000101）**，在本格自测的配对噪声（max|Δ| = 0.000101）
   下**不可分辨**。关键是这个摊薄**不牺牲「过去的读数绝不被未来影响」**：标尺只由当前 token 自己的值
   决定，前缀不变性两条均为 True。
2. **「省一半」只在一种实现下不成立**：逐值标尺（`2631` 的生产实现）⇒ int8 = 3 B/值 = fp16 的 **1.5×**，
   反占内存。沿 token 轴摊薄（把 32 个相邻位置合成一块，`block_tok` / KIVI 的 K 侧）也能省到 1.0625 B/值，
   但代价是**块内过去位置的读数会被同块后续位置改写**（违反前缀确定 ≤ 31 个位置）——它不是免费的另一条路。

**顺带一句 int4。** int4 在块标尺下省 **71.9%**（3456 字节/位置），但质量**确有损伤**：+0.0225（纯量化臂），
在头共享组合臂上更差（+0.071 / +0.161）。所以 int8 是「近无损 + 省一半」，int4 是「省更多 + 有损」，
两者不是同一档。

## 2. 正面对照：新数字 vs 旧数字

**部署口径**：`2631` 的 (a) = 逐值标尺（每值 +2 B）；本实验主臂 = 块标尺沿 `head_dim G=32`（每值 +0.0625 B）。
非量化臂两列相同。Δbpc = 本实验 block − `2631` per_value（**负 = 块标尺质量更好**）。fp16 基线 = 1.483571，
不压部署字节 = 12288。

| 臂 | 2631 bpc（逐值标尺） | 2632 bpc（块标尺） | Δbpc | 2631 部署(a) | 2632 部署(block) | 新×fp16 | 新省幅 | copy 召回（2631→2632） |
|---|---|---|---|---|---|---|---|---|
| `fp16` | 1.483571 | 1.483571 | +0.000000 | 12288 | 12288 | ×1.00 | — | 0.1413→0.1413 |
| `int8` | 1.483688 | **1.483672** | −0.000016 | **18432（×1.50，反占）** | **6528** | **×0.53** | **−46.9%** | 0.1416→0.1406 |
| `int4` | 1.508319 | **1.506093** | −0.002226 | 15360（×1.25，反占） | **3456** | **×0.28** | **−71.9%** | 0.1270→0.1305 |
| `gqa_int8` | 1.496412 | 1.496441 | +0.000029 | 4608 | 1632 | ×0.13 | — | 0.1680→0.1683 |
| `mqa_int8` | 1.493961 | 1.493933 | −0.000028 | 2304 | 816 | ×0.07 | — | 0.2412→0.2448 |
| `gqa_int4` | 1.543484 | 1.553126 | **+0.009642** | 3840 | 864 | ×0.07 | — | 0.1504→0.1462 |
| `mqa_int4` | 1.587956 | 1.642750 | **+0.054794** | 1920 | 432 | ×0.04 | — | 0.1950→0.1849 |
| `win32_int8` | 1.695436 | 1.695617 | +0.000181 | 2304 | 816 | ×0.07 | — | 0.0143→0.0143 |
| `win64_int8` | 1.564140 | 1.564194 | +0.000054 | 4608 | 1632 | ×0.13 | — | 0.0592→0.0599 |
| `win16_anchor16_int4` | 1.912605 | 1.911669 | −0.000936 | 1920 | 432 | ×0.04 | — | 0.0586→0.0560 |
| `win32_anchor32_int4` | 1.621580 | 1.622484 | +0.000904 | 3840 | 864 | ×0.07 | — | 0.0902→0.0804 |

**读法**：

- **纯量化与 int8 组合臂**：块标尺与逐值标尺的质量**差异在自测带宽内**（|Δ| ≤ 0.0002）⇒ int8「近无损」
  结论**保留**，但字节从「反占 50%」变成「省 46.9%」。
- **int4 组合臂（头共享）**：块标尺质量**明显更差**（`mqa_int4` +0.0548）。原因：块标尺（每 token
  一整行共享一把）丢掉了**逐通道分辨率**，而 int4 只有 16 级、通道离群值会吃掉量程；逐值标尺的
  `cummax` 在「每通道 × 每 token」上自适应，对 int4 更友好。⇒ **块标尺对 int4 不是免费午餐**（见 §4）。
- **等字节下另一条路**：沿 token 轴分块（`block_tok G=32` / KIVI）同样是 3456 字节/位置，但 int4 质量
  更好（1.4979 / 1.4969）——代价是**违反前缀确定**（见 §5）。

## 3. 部署字节账（值 + 标尺 + staging）

**公式**：`部署字节/位置 = 2(K,V)·L·n_kv_heads_eff·head_dim·(value_bytes + scale_bytes_per_value)·(kept/T)`。

**标尺每值字节（本实验实现，与 `kv_quant.quantize_kv(scheme=...)` 一一对应）**：

| 方案 | 标尺轴 | 每值标尺 | 前缀确定 | int8 B/值 | int4 B/值 | int8 省幅 | int4 省幅 |
|---|---|---|---|---|---|---|---|
| `per_value`（对照，2631） | token（running） | 2.0 | ✔ | 3.00 | 2.50 | **−50%（反占）** | **−25%（反占）** |
| `block` G=8 | head_dim | 0.25 | ✔ | 1.2500 | 0.7500 | 37.5% | 62.5% |
| `block` G=16 | head_dim | 0.125 | ✔ | 1.1250 | 0.6250 | 43.8% | 68.8% |
| **`block` G=32（主臂）** | head_dim | **0.0625** | ✔ | **1.0625** | **0.5625** | **46.9%** | **71.9%** |
| `block_tok` G=32 | token | 0.0625 | ✘（≤31 位置） | 1.0625 | 0.5625 | 46.9% | 71.9% |
| `kivi` G=32 | K: token / V: head_dim | 0.0625 | K✘ V✔ | 1.0625 | 0.5625 | 46.9% | 71.9% |

- **`head_dim = 32` ⇒ 沿 head_dim 的块上限 = G=32**（= per-token 标尺）。G=64 要求块跨 token，**无法同时
  保持前缀确定**：标尺一旦跨 token 就必须么（a）用整块 max（块首位置的存储值被未来改写），么（b）保持
  前缀但标尺随前缀变化（不再摊薄）。⇒ **「省 50%」的极限在 G=32 处取到 46.9%**，再往下压只能让出因果。
- **staging（非因果方案的额外记账）**：沿 token 分块的回填必须留住原始 fp16 值 ⇒ 每请求 `G` 个位置的
  fp16 KV = **393216 B/请求**（G=32；折合 T=256 时 1536 B/位置，与目标精度无关、int4 也要留）。
  本表未把 staging 混进每位置列（它随 T 变小），单列在此。
- **实测显存**：评测期 GPU 峰值 **1798.6 MiB**（`torch.cuda.max_memory_allocated`）。评测实现把 K/V
  **立刻反量化** ⇒ 峰值不随档下降，**不是内存价签**（判据 C2，解析/实测分列）。

## 5. 三道对账（SCHEMA §12）

1. **算术对账**：部署字节 = 值 + 标尺，逐点对账（`scale_caliber.deployment_bytes` 内部断言与判据 C1
   的旧值字节逐位一致，对不上直接报错）。`int8` 每值 = `1 + 2/32 = 1.0625`、每位置 = 6144·1.0625 = 6528
   （不压 12288 ⇒ 省 46.875%）；`per_value` 每值 = `1 + 2 = 3`、每位置 18432（= 1.5×）。取整误差上界
   `|x̂ − x| ≤ 0.5·块标尺`（单测钉住；`clipped_frac = 0.58%` 是块内 amax 位置的浮点边界，非真剪裁）。
2. **任务对账**：质量两腿与 `2631` 同任务、同数据流、同位置集（`bpc_of` 逐位复现）；**质量数字与
   `block` 价签同源**（同一 `quantize_kv(scheme="block")` 前向）；非因果方案（`block_tok`/`kivi`）的
   质量数字**单列**，不挂到 `block` 的字节上。评测峰值不随档下降已单列。
3. **口径对账**：T = 256 固定；窗口/锚点臂 `kept/T` 与 T 有关（禁外推到别的 T）；量化臂每位置字节与 T
   无关；本批是**快照口径**（冻结 checkpoint，单 seed 训练、单 T、`head_dim=32`）。
   **本格自测方差**：同臂跨 3 个评测窗口的单臂 bpc 极差 = 0.036324（主要来自**窗口数据**本身），
   而**配对量** `int8(block) − fp16` 逐 seed = [0.000101, 0.000013, 0.000009]、max|·| = **0.000101**
   ⇒ 同一窗口下两臂共享同一批数据，比较是配对的；「int8 近无损」按配对口径读（不可分辨）。

## 6. 干预活性、对照与可控性

- **干预活着**：`int8` 块标尺的活性量 `n_values = 6291456`、`changed_frac = 0.970`、`rel_err = 0.00487`、
  `scale_min = 0.0030`、`scale_max = 0.1092`（`results.json::points[*].activity`）；`int4` 同族且更糙。
  窗口/锚点臂报掩码挡掉的因果对数；头共享臂报真实 K/V 张量形状。
- **对照臂可比性**（SCHEMA §13）：`per_value` 与 `fp16` 在同表同任务；chance = 0.0156；局部先验（最近 8
  token）= 0.0146；逐臂毁源对照见 `points[*].recall_copy_source_corrupt`。
- **可控性**：非量化臂与 `2631` 逐位一致（`max|Δbpc| = 0`）；`scheme="per_value"` 前向与生产前向逐位一致；
  `--charts-only` 可纯 CPU 重生成表。

## 7. 失败与局限（「以为会怎样 / 实际怎样 / 为什么 / 排除了什么」）

1. **以为**：把标尺从逐值改成块标尺，质量只会略变、字节大幅下降——两边都赚。
   **实际**：int8 与 int8 组合臂确实如此；但 **int4 组合臂质量反而更差**（`mqa_int4` +0.0548）。
   **为什么**：块标尺（每 token 一整行共享一把）丢掉了逐通道分辨率；int4 只有 16 级，通道离群值会
   吃掉量程。**排除的解释**：不是「实现坏了」（单测+变异抓红、误差上界恒成立）、不是「换了任务/模型」
   （非量化臂逐位不变、bpc 与仪器逐位相等），而是**块标尺与 int4 的匹配问题**——沿 token 轴的
   per-channel 块（`kivi`/`block_tok`）在 int4 上更好，但它违反前缀确定。
2. **以为**：`head_dim` 分块本应能摊到 G=64、G=128，省幅趋近 50%。
   **实际**：`head_dim = 32` ⇒ 沿 head_dim 的块**上限就是 32**；G>32 只能跨 token，不可能同时前缀确定。
   **排除的解释**：不是「做不到摊薄」，而是**可摊销的轴只有非 token 轴**，其宽度就是 `head_dim`。
3. **局限**：① 单 seed、单规模（13.5M）、单 T（256）、`head_dim=32`、快照口径；② 质量数字只覆盖
   列出的方案（未测 fp8 标尺、旋转/投影类量化、权重/激活量化）；③ 「KIVI」为 `记忆·未核`（本机联网
   不可用，未核对原文）；④ 本实验只做**推理期存储精度**，不改权重、不改结构。

## 8. 结论（判据 ⑤）

- **「8 位近无损且省约一半」这条参照线成立**，条件是**沿 `head_dim` 摊薄标尺**（块标尺 G=32）：
  int8 每位置 12288 → **6528 字节（省 46.9%）**，clean bpc 1.483571 → **1.483672（+0.000101）**，
  在本格自测的**配对噪声 0.000101** 下不可分辨；且**前缀不变性成立**（未来 token / 同批邻居都不改过去读数）。
- **在什么实现下不成立**：**逐值标尺**（`2631` 的生产实现）⇒ int8 = 3 B/值 = fp16 的 **1.5×**，
  反占内存。这正是本仓此前「量化在任何拓扑上都是内存负收益」的来源。
- **int4 是另一档**：块标尺省 **71.9%** 但质量有损（+0.0225 纯量化臂；头共享组合臂更差）。
- **沿 token 轴分块**（`block_tok` / KIVI 的 K 侧）同样省 46.9%，但**违反前缀确定 ≤ G−1 个位置**，
  且需 staging（393216 B/请求 @G=32）——不是免费的等价替代。
