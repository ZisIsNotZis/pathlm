# 2621 · 搬运通道 × KV 精度压缩 —— 判读

## 0. 人话摘要（先看这段）

**我们在问什么。** 这个模型有一个「把信息往右搬」的小通道：它在只看得见**最近 16 个
位置**的情况下，靠一个固定大小的记忆矩阵把更早的 key→value 记下来、答出后面的提问。
我们已经有正面结果——**这个通道真的有用**（无通道时关联回忆 1.37% ≈ 乱猜，加通道后
9.50%）。另有一条独立正面结果——**把注意力的 KV 缓存压成 int8 几乎不掉质量**。
本实验把两者叠起来：**给注意力的 KV 缓存做 int8 压缩，会不会把「搬运」弄坏？**

**一句话结论：不会。在这个任务、这个尺度上，int8 级压缩与搬运通道兼容。**

- 关联回忆（窗口外的 key 能不能被问出来）：
  **int8 = 9.28%** vs **全精度（fp16）= 9.38%** —— 差 **0.10 个百分点**（判据线是「不崩」
  即 ≥ −3pp；若 CI 不重叠且更低才算「崩」）。**没过崩线。**
- 省了多少内存：每位置 KV 字节 **12288 → 6144（−50%）**（解析口径，MHA）。
- 语言建模质量（clean bpc，越低越好，跑在 enwik8 尾段）：**103.6093 vs 103.6118**，
  差 **−0.0025**（int8 甚至略好）。这个差远小于本项目 0.014 的可排序界 ⇒ **测不出损伤**。
- 通道活性没变：每层「记忆读出占注意力输出量级」的比例 **0.34217 → 0.342165**
  （差 5e-6，量化噪声级）⇒ 压缩没有把通道读出挤掉。

**必须显式声明的局限（详见 §4b）。** 契约原设计想叠的是「**GQA × int8**」这整套压缩
（GQA 少 75% 的头、int8 再少一半字节）。但引擎**硬禁止** GQA 与「搬运通道」、
GQA 与「窗口 16」同时开启（两个 `ValueError`，见 §4），而窗口 16 恰恰是制造「必须搬运」
需求的前提。因此经主 Agent 裁决，本实验**只测了 int8 这一个因子，GQA 因子未测**：
结论**不得外推**到 GQA/MQA/组合压缩，只能表述为「**int8 级量化与搬运通道兼容（该任务/
该尺度）**」。

---

## 1. 它是干什么的（六问之①）

让模型在**局部先验无法补全**的合成任务（多查询关联回忆）上，把「只见过一次、且已经
滑出可见窗口」的 key→value 对应记住并在后面答出来。这是「长程信息搬运」的直接读数。

## 2. 相对普通的 decoder-only transformer 改了什么（六问之②）

- 基底 = stock dense decoder-only（13.5M：d256 × 12 层 × 8 头 × mlp6 × T256）。
- 改动 = **一个显式写入通道**（ticket 35 的 `U2` 臂）：一个固定大小的
  `S ∈ R^{dh×dh}`/头 的**单共享记忆槽**，在输入流上逐位置**残差写**
  `S ← S(I − βk̂k̂ᵀ) + βvk̂ᵀ`（delta rule，只写「上次没写进去的」），每层再按一个
  可学读出增益 `γ` 把 `S q` 加进注意力输出。注意力本身**仍只看最近 16 个位置**。
- 量级：新增 **264,296 参数（+1.95%）**；状态大小 **与序列长度无关**（8192 floats）。
- **本实验不改这个通道**，只把注意力的 **K/V 存储精度**从 fp16 降成 int8
  （评测期，不改权重、不加参数）。

## 3. 为什么要改（六问之③）

部署长上下文时，KV cache 的**访存**是瓶颈；GQA/量化正是业界为此做的两件事。
如果「省内存」的代价是「搬运失效」，那这条路就不能走。本实验回答的就是这个交互。

## 4. 怎么测的（六问之④：对照 / 指标 / 口径）

- **对照组**：同一检查点（ticket 35 的 `U2`，sha256 断言）的 **fp16（全精度 KV，工业默认）**；
  另报 `fp32`（释放版，作实现等值锚，必须逐位相等）。
- **主指标**：合成长程任务 `assoc_recall`（K=8、窗口 16、`frac_outside_window = 1.0`）
  的 top-1 准确率 + Wilson 95% CI；**辅助腿**：clean bpc（enwik8 尾段）+ 变距离回忆。
- **口径**：**评测期**（不训练）、**合成任务**（SCHEMA §19，不用 enwik8 当长程主任务）；
  字节用**解析**口径，实测显存单列。
- **三道护栏**：① 前提（key 100% 窗外）；② **毁源对照臂**（把源片段换掉后读数必须落回
  chance）；③ 活性（量化真的改数值 + 通道真的被读）。

## 5. 测出来多少（六问之⑤：数字 + 参照系 + 人话量级）

**主腿（关联回忆，n=2048/arm）**

| mode | 准确率 | Wilson 95% CI | 毁源后 | 每层 read_share |
|---|---|---|---|---|
| `fp32`（释放版锚） | **9.38%** | [8.19%, 10.71%] | 0.73% | 0.34217 |
| `fp16`（全精度基线） | **9.38%** | [8.19%, 10.71%] | 0.73% | 0.34217 |
| `int8`（压缩） | **9.28%** | [8.10%, 10.61%] | 0.73% | 0.342165 |

- **Δ(int8 − fp16) = −0.098pp**，两臂 CI **重叠**（`z = −0.107`, `p = 0.914`）⇒
  **未「崩」**（判据 ①：崩 = Δ < −3pp **且** CI 不重叠）。
- 参照系：chance = 1.5625%，局部先验地板（只看最近 8 个 token）= 3.125%。三臂都在
  chance 的 ~6 倍 ⇒ 读数确实来自「搬过去的信息」。**毁源后 0.73% < chance**，方向正确。
- **人话量级**：9.38% → 9.28%，相当于每 1000 道题少答对约 1 道；判据线是「少答对 30 道
  才算崩」，所以**远没到崩**。

**字节/位置（判据 ②，解析口径）**

| mode | 每值字节 | 每位置字节（MHA, 12 层） | 相对 fp16 |
|---|---|---|---|
| `fp32` | 4 | 24576 | 释放版锚（无压缩） |
| `fp16` | 2 | **12288** | 基线 |
| `int8` | 1 | **6144** | **−50%** |

（int8 另加与序列长度无关的 scale 开销 12288 B 总计；T=256 时折合每位置 +48 B。）

**clean bpc（辅助腿，越低越好）**

| mode | bpc | Δ vs fp16 |
|---|---|---|
| `fp32` | 103.611675 | −0.000115 |
| `fp16` | 103.611790 | 基线 |
| `int8` | 103.609283 | **−0.002507** |

`|Δ| = 0.0025 < 0.014`（本项目方差界）⇒ **测不出 int8 的语言建模损伤**（甚至略好，
属噪声）。absolute bpc 很高是因为该模型只在合成任务上训练过——这里看的是**差分**。

**距离腿（辅助腿，fp16 vs int8 逐点对照）**

| 距离 | 16 | 32 | 64 | 128 | 192 | 255 |
|---|---|---|---|---|---|---|
| fp16 | 0.062 | 0.000 | 0.276 | 0.083 | 0.000 | 0.578 |
| int8 | 0.062 | 0.000 | 0.276 | 0.083 | 0.000 | 0.578 |

**逐点逐位相同**（n=192/点）⇒ int8 在整条距离曲线上都没改变读数。曲线**非单调**
（§17.11：单点不外推）。

## 6. 结论与下一步（六问之⑥）

- **采纳（有限口径）**：`int8` 级 KV 量化与「delta 写搬运通道」在该任务/该尺度上**兼容**；
  每位置字节 **−50%**，召回与 clean bpc 均测不出损伤。
- **不采纳 / 未测**：**GQA/MQA 头因子未测**（引擎硬互斥，§4b）；结论**不外推**到组合压缩。
  按 SCHEMA §19，这只是「在该任务/该尺度上成立」，**不是**「压缩机制不可能/必然兼容」。
- **下一步最小实验**：见 §9「未测项」。

## 4b. 与契约原设计的偏离：GQA 因子未测

契约原设计为 `delta 通道 + 全精度 KV` vs `delta 通道 + GQA×int8 KV`。执行前实测发现
引擎**硬禁止**该组合（未碰任何共享文件即停下请示，主 Agent 裁决走 A 方案）：

| 组合 | 结果 | 位置（`pathlm/depth_ar.py`） |
|---|---|---|
| `carry_rule` ⊕ `n_kv_heads < n_heads` | `ValueError: carry_rule 与 n_kv_heads < n_heads 互斥` | 1690–1711 |
| `n_kv_heads < n_heads` ⊕ `train_window > 0` | `ValueError: n_kv_heads 与 train_window 互斥` | 1712–1734 |

且块类是二选一的（`GQABlock` **或** `CarryChannelBlock`）。窗口 16 是制造「必须搬运」
需求的前提（key 100% 窗外），因此 **GQA 无法与搬运通道/窗口共存**。放开它需要改
`depth_ar.py` 的架构校验并新增组合块——违反本契约「不改引擎」，且与 W4 线抢共享文件
（SCHEMA §22 代码锁）。

**因此本实验只回答「int8 量化对搬运的干扰」**，`int8` 臂 = MHA + int8（GQA = 0 因子）。
「全精度 KV」臂落为 `fp16`（工业默认，与 2614/2619/2620 同口径）。**参数量混杂已消失**
（int8 量化新增 0 参数）；原契约提醒的 GQA −8.75% 混杂**不适用**（未测）。后续有界任务
`ENG1`（让 GQA × carry × window 可组合）由主 Agent 另排。

## 8. 三项护栏（判据 ③④，SCHEMA §10）

- **前提校验**：`frac_outside_window = 1.0`（key 距离 241–255，窗口 16）⇒ 需要搬运；
  chance 1.5625%、局部先验 3.125%，模型三臂均 ≈6× chance。
- **毁源对照臂（判据 ③）**：三臂毁源后均为 **0.7324%**（CI [0.44%, 1.21%]），
  **低于 chance**⇒ 读数确来自被搬运的源信息，无一臂被判「作废」。
- **活性（判据 ④）**：
  - 量化侧：`fp16` `rel_err = 1.76e-4`、`changed_frac = 0.9999`；`int8`
    `rel_err = 4.36e-3`、`changed_frac = 0.9998`、`clipped_frac = 3.82e-5`
    （`n_values = 3.22e9` 累计）⇒ 量化**真的改了数值、且 int8 比 fp16 狠**。
  - 通道侧：`carry_liveness.alive = True`（`state_fro = 3.73`、`beta_mean = 0.511`、
    `write_rel = 0.798`、`read_scale_absmean = 0.0752`、
    `rel_dev_vs_channel_off = 0.0226`）；每层 `read_share ≈ 0.387`。
  - **「每 200 步」**：本实验是 **eval-only**（不训练）⇒ 无训练步。被复用检查点的
    训练日志（`2618/train/U2/train_log.jsonl`）提供每 200 步的通道活性（60/61 行落在
    200 的倍数；末值 `read_share = 0.7103`、`state_fro = 3.072`）。本实验自身的量化
    活性量**按批落盘**（`results.json::bpc_leg[*].per_batch`）。

## 9. 未测项（显式列成最小实验 + 成本）

1. **GQA × carry × window 组合**（本契约原设计）：需 `ENG1` 引擎改造（把 KV 头投影从
   block 类解耦 + 窗口掩码装饰化 + 组合可失败单测），有界但需串到 W4 之后。
   成本 ≈ 2 臂 × 13M × 12k 步 ≈ 30 min。
2. **MQA / int4 档**：`int4` 在 2614 已知有明显损伤；叠加搬运通道未测。成本 ≈ eval 3 min。
3. **更长序列 T 上的交互**（我们 T=256 固定）：SCHEMA §19 的限制，扩 T 需先解决位置编码。
4. **训练期就用量化 KV**（本实验是评测期压缩）：会不会让通道学得更依赖/更不依赖注意力，
   未测。

## 10. 复现性

- 同 seed、同代码、同设备把主腿 `fp16` 与 `int8` 各再跑一遍：`n_hits` 两次完全相同
  （21/21、20/20），`max_abs_diff = 0.0` ⇒ `pass = true`。
- `fp32` 档与释放版前向 `max|Δlogit| = 0.0`（逐位）⇒ 量化前向不是「另一个模型」。

## 11. 成本与 §20.1 登记

- 评测墙钟 **0.92 min**、峰值显存 **431.6 MB**（净分配）。预算 `10 min`，远未触顶。
- **§20 一次性并发例外登记**：运行期间 GPU 锁由 W4 线的 `perdepth` 训练持有
  （`holder_pid = 1011253`，非本次）。本实验为**纯推理、墙钟 < 2 min、峰值 431.6 MB
  < 1 GB**，且 `nvidia-smi` 空闲 **≥ 3 GB**（运行前 15.0 GB / 运行后 15.0 GB 空闲），
  符合 SCHEMA §20.1 第 2 条的短任务插队条件；**未取锁、未动锁目录**。
