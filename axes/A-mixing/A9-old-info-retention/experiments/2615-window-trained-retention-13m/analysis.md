# analysis · 2615 · 窗口训练后依赖是否「右移」（13M dense，ticket 32 契约 O）

## 1. 人话摘要（先看这一段）

用户最初的设想是：**「把模型训练成只用近处，它就会把信息往右压，于是左边的前缀可以丢掉而
质量不掉。」** 我们把这个设想拆成三个能分别证伪的问题，在同一件天平上直接测了。

做法很朴素：同一个 13.5M 的小变压器，训练两次——一次正常（什么都能看，直接用仓库里已有的
那个模型，没重训），一次**训练时只允许看最近 32 个字符 + 开头 8 个字符**（「锚点」）。两次
除了这个可见窗口以外，其它一切都一样（同样的 12000 步、同样的批大小、同样的随机种子）。
然后拿两件仪器量它：一件量「砍掉某段上下文，质量掉多少」（依赖），一件量「把一段内容藏在
窗口外，它后来还答不答得出来」（保留）。

三句话结论：

1. **窗口训练不是免费的**：训练成只看近处，clean bpc（每字符比特数，越低越好）从
   **1.4836 掉到 1.5701**，差了 **0.0866 bpc**——是普通变压器基线的一成半左右的差距（换成
   人话：同样的模型，把可见范围砍到 32 个字符，语言建模精度损失约 5.8% 的相对 bpc）。
   这落在历史 X2 记录的同一条带上（契约记 +0.058~0.121）。代价**不是零，也远大于 0.014 的
   可分辨门槛**。
2. **「依赖右移」这条没测出来**：想要成立的证据是「window32 在距离 8~32 上被砍掉时，伤害
   明显比 full 小」。实测在预登记口径下 gap 均值只有 **+0.0008 bpc**（门槛 0.014）——几乎
   正好是零；换到它真正的工作点口径（窗口掩码为基线）也只有 **+0.0133**，仍然差一点不到
   门槛。方向上确实「window32 对 8~32 的依赖略小」，但**幅度没到可排序线**，判据②**未过**。
3. **「保留了信息」这条明确否证**：把针（一段真实文本短语）埋在窗口外，答案行看不到它。
   如果信息被「搬到了近处」，它应该还能答出来。实测：window32 在窗口外的针上召回
   **0.4588**，而**同一掩码、同一批针、只是不植入内容**的「无记忆地板」是 **0.4545**——
   差 **+0.004**，即**与「完全没有记忆」没有区别**。而在窗口**内**的针上它召回 0.6506
   （地板 0.4458，+0.205）——说明它检索的能力没问题，是**信息真的不在**。
   **是「丢了」，不是「搬了」**（这正是 X3「假保留」陷阱的实例）。

**换句话说**：前缀确实可以丢，但原因不是「信息被压缩搬到了右边」，而是**「模型根本没学到
需要它」**；而且为了让模型「不需要」，你付出了 0.0866 bpc 的质量税。低损伤 ≠ 保住了信息
（SCHEMA §17.10 的判据陷阱在这里被正面撞上）。

**负结果已复现**：为满足「n=1 的负结果必须复现后入账」（methodology §2），整条 window32 臂
**同配置重跑了一遍**（同 seed、同 12000 步）：税 **0.0821**（vs 0.0866）、判据②均值
**+0.0014**（vs +0.0008，仍 ≈ 0）、窗口外针 gap **−0.0046**（vs +0.0043，仍 ≈ 0）——三条
结论完全一致（`stability.md §3.2`，重跑电池在 `rep/results.json`）。

## 2. 六问（面向用户，逐问回答）

1. **它是干什么的**：让模型在推理时只依赖最近的一小段文本，从而历史前缀可以被安全丢弃
   （KV 压缩 / 滑动窗口部署）。
2. **相对普通的 decoder-only transformer 改了什么**：**结构上什么都没改**——参数量、
   层数、宽度、读出方式逐位相同（13,536,768 参数，两臂一样）。唯一改动是**训练时的注意力
   可见集**：每个字符只允许看「距离 < 32 的位置」以及「最前面 8 个锚点位置」，其余键在
   训练前向里被掩掉。计算量/显存增量可忽略（实测步时 39.0 ms vs 37.8 ms，1.03×）。
3. **为什么要改**：如果依赖可以被训练成局部的，那么长上下文的内存/墙钟开销可以砍掉
   （A9/A10 两条线的前提）。
4. **怎么测的**：两臂都跑同一件天平——① 依赖腿：在**同一批评测窗口**上删除指定位置的
   KV，测 bpc 的损伤（距离曲线 / 左前缀曲线 / 只留最近 d 曲线）；② 检索腿：在 256 长度的
   窗口里植入 8 根真实文本「针」，看答案行能不能把针的下一字符答对（分母分桶：锚点 / 窗口内 /
   窗口外）。对照组：`full` 臂（同配方、全可见、复用 2610 的 `trunk.pt`，sha256 断言）。
5. **测出来多少**：见上面「人话摘要」的三句话 + 下面的数据表；参照系一律是**同尺寸、同配方、
   同步数的 `full` 臂**，不是 oracle、也不是更大的模型。
6. **结论与下一步**：**用户这个设想在 13M / 256 上下文 / 12k 步的快照上不成立**（不是实现
   问题：掩码训练/评测一致、活性量非零、变异验证 5/5 抓红）。若要继续，应换尺度（更大模型
   /更长训练，看质量税是否随规模缩小）或换机制（显式的记忆压缩/摘要写入，而不是靠注意力
   掩码「逼」出压缩）。

## 4. 判据达成（逐条，判据线未改）

| 判据 | 预登记要求 | 实测 | 达成 |
|---|---|---|---|
| ① 质量 | `window32` 相对 `full` 的 clean bpc Δ（阈值 0.014；历史 X2 +0.058~0.121） | native 口径：1.483569 → **1.570135**，Δ = **−0.086566**；release 口径 Δ = **−0.223798** | **有显著质量税（0.0866 bpc，6× 阈值）** ⇒ 「不掉质量」不成立 |
| ② 依赖右移 | 「window32 在 d ∈ [8,32] 上的伤害显著**小于** full」 | gap(=`damage_full − damage_window32`)：d=8 **−0.0131**、d=16 **+0.0094**、d=32 **+0.0060**，均值 **+0.0008**（主口径）；工作点口径均值 **+0.0133** | **未过**（主口径 ≈ 0；次级口径 0.0133 < 0.014） |
| ③ 保留成立 | 「window32 能答出原本位于窗口外的针」 | 窗口外召回 **0.458773**（n=3505）vs 同掩码无针地板 **0.454494** ⇒ gap **+0.0043**（门槛 0.10）；更难子集（地板答不出的针）beyond 召回 **0.0371**（n=1912） | **未过** ⇒ 「**丢了**」，不是「搬了」 |

**判据 ① 的方向说明**：Δ 定义 `Δ = bpc_对照(full) − bpc_实验(window32)`（正 = window32 更好）。
本实验 Δ 为负 ⇒ window32 更差。契约把阈值 0.014 用在「质量差是否可分辨」上，历史 X2 的税是
+0.058~0.121；本次 0.0866 落在该带内，属于**同一结论的复现**而非新发现。

  上是 1.570135）。**唯一诚实的比较是「相对各自同掩码地板」**：`full` 的 beyond gap =

- 构造检查：`full`/release/植入 = **0.686768**，与契约 M 记录的基线 0.686768 **逐位相同**
  （同一构造序列 ⇒ 同一批针），地板 0.4331 也与 M 一致 ⇒ 构造未带病（≥50% 门槛）。

**判据 ③ 的结论**：**信息没有被搬到近处**。前缀可以丢，但代价是「当时就没学」。

### 6.2 任务对账

对照臂三要素（SCHEMA §13）：

| 对照臂 | 输入分布 | 要预测什么 | 部署中对应什么 |
|---|---|---|---|
| `full`（release） | enwik8 尾 10M 的同一批 24×16 窗口（`window_seed=2`） | 下一个字符（行 i → t_{i+1}），**同一位置集** | 不删 KV 的基线部署 |
| `full`（native 窗掩码） | **同上**（同一批窗口、同一批针） | 同上 | 滑动窗口部署下的现有模型 |
| 针的无针地板（`plant=False`） | 同一批针位/线索、同一掩码，只是窗口里**不植入短语** | 同一根针的下一字符 | 「内存里没有这条信息」的对照物 |

- **同一输入分布 / 同一位置集 / 同一预测对象**：两臂用**同一批**评测窗口（`window_seed=2`，
  24×16），检索腿用**同一批针**（同 seed、同 generator 状态、`plant=True/False` 配对，
  `meta` 逐字段相同的断言在 `run.py` 里强制执行）。
- **对照臂是不是在测同一件事**：判据②的对照是**同一模型自己的 release 路径**（同引擎、
  同数据流、同窗口），不是跨 run 对照；检索腿的对照是**同一掩码、同一批针的无针地板**
  （唯一差别 = 窗口里有没有那段短语）⇒ 不是「假上下文 + 真目标」。
- **仪器同一性**：`full` 臂的 release 数字与 2614 记录 **max|Δ| = 0.0**（9 个距离点 + 7 个
  前缀点 + 基线全部逐位吻合）⇒ 两个实验用的是同一件天平。
- **针构造的带病检查**：`full`/release 基线召回 0.686768 ≥ 0.50 门槛，且与契约 M 记录逐位
  相同 ⇒ 构造健康、可判读（SCHEMA §17.10）。

### 6.3 口径对账

| 口径 | 本实验的处理 |
|---|---|
| 快照 / 渐近 | **快照（matched-step 12k）**；两臂同 12k 步、同 98.304M tokens、同 lr 调度。**未跑 2×（24k）点**（契约固定 12k 步；见 §8 残余风险） |

| 为什么必须双报 | `window32` 的 **release 口径本身是 OOD**：训练时从未见过距离 ≥32 的键，全可见时 bpc = 1.707367，**比它的 native（1.570135）还差 0.137232**。这解释了 §5.2/§5.3 里「删掉远处反而变好」的负 damage ——它不是「右移的收益」，而是「没见过的键在添乱」 |

## 7. 失败归因与失败决策树

### 7.1 决策树（提前登记在 `README.md §10`，此处按实际结果走一遍）

| 症状 | 诊断 | 本实验的处置 |
|---|---|---|
| 判据 ①② 无差异、判据 ③ 与地板同水平 | 训练期窗口无头寸 | **本次命中的是「①②有差异但不够、③与地板同水平」**：先按「测量问题→实现问题→规模问题」排除（下三节），失败不可归因于测量/实现 ⇒ 记为「设计在该规模下无效」 |
| 判据 ③ 有召回但 `window` 桶也崩 | 掩码不一致 / 针构造带病 | **未命中**：窗内桶 0.6506 > 地板 0.4458（阳性对照健在）；`train_mask_equals_eval_mask=true`；构造基线 0.6868 ≥ 0.50 |
| 曲线非单调、超出噪声容差 | 测量问题 | **未命中**：三条曲线在噪声容差内单调（与 2614 同构）；仪器自检逐位 |
| 两臂 Δbpc 与训练日志矛盾 | 口径问题 | **部分命中**：native/release 两个口径给出的 window32 bpc 差 0.137 ⇒ 已双报（§6.3） |
| 结果不可重复 | 方差 | **已处理**：评测侧 4.31e-07；训练侧同配置 12k 重跑差 0.0045（`stability.md §3.2`），判据三条结论一致 |

### 7.2 排查顺序与结论

按 methodology §14 的顺序排查：

1. **测量问题** → 已排除：仪器自检（release==identity 逐位；训练掩码==评测掩码逐位、
   max\|Δlogit\| = 0.0）、同 seed 重跑 4.31e-07、与 2614 记录 max\|Δ\| = 0.0、针构造
   基线 0.686768 与契约 M 逐位相同。
2. **实现问题** → 已排除：8 条新单测全绿、变异验证 5/5 抓红（掩码丢锚点 / 窗口 off-by-one /
   前向没传掩码 / 忽略 window / 锚点取错端），破坏后逐字节还原（sha256 一致）。
   另有 1 处**冗余防线**（`| eye`）如实登记：在本掩码族里 window ≥ 1 时窗口项已含对角，
   删掉它无可观测行为差异（见 `mutation_report.json::M4`）——不作为测试有效性证据。
3. **规模问题**（13M / 256 上下文 / 12k 步是否有头寸）→ **未能排除**：窗口 32 相对 256 的
   上下文只剩 1/8，税 0.0866 与 X2 历史同带 ⇒ 至少「税」这一侧是稳健的；但「右移」这一侧
   在更长训练/更大模型上是否出现，本实验**没有数据**（未跑 2× 点）。
4. **设计问题** → 在本次数据范围内，结论是：**「靠注意力掩码逼出信息搬运」在该规模不成立**
   （信息既没保住也没搬走，只是不再被需要）。
5. **口径/判据问题** → 判据②在主口径下 ≈ 0、在次级口径下 0.0133，都低于门槛且低于训练噪声
   ⇒ 如实报「未过」，**不调判据线**。

## 8. 残余风险与未完成项

1. **训练侧不可逐位复现**（项目级已知事实）：本实验**实测**了它——同配置 400 步重跑在
   step 399 差 0.0108 nats（≈0.0156 bpc）；**整条 12k 臂**同配置重跑后 native 口径
   clean bpc 差 **0.0045**、release 口径差 **0.0661**（后者是 OOD 口径，放大）。
   判据①（0.082~0.087）是训练噪声的 ~20× ⇒ 安全；判据②（0.0008~0.0133）与判据③
   （±0.005）在该噪声量级内 ⇒ 「未过」是保守但正确的读数，**不能用它们反推「确实没有
   右移」的强结论**。
2. **未跑 2×（24k）训练点**（SCHEMA §16 的收敛对账）：契约固定两臂 12k 步，24k 点需再训
   ~8 min/臂。两臂同方法 loss 斜率已给出（见 `results.json::convergence_reconciliation`）：
   全程最小二乘斜率 full −9.7588e-05 vs window32 −9.5429e-05 nats/step，末 25%（9k–12k）
   full +1.177e-06 vs window32 +3.43e-07（**两臂都基本平了**，不是「一臂还在猛降」）；末行
   loss full 1.0110 vs window32 1.0468 nats。⇒ 快照结论只能标为「12k 快照」，是否随训练
   拉长而收敛未测。
3. **判据②的混杂**：`window32` 整体更弱（+0.0866 bpc），更弱的模型天然有更平的损伤曲线；
   本实验无法把「依赖右移」与「整体变弱」分开。
4. **贴窗带的样本量小**：beyond 的 [0,32) 带只有 54 根针（+0.13 的信号，n 太小不作判据）。
5. **本实验未做**（契约未要求、也不在授权范围）：更大规模/更长训练；`fill_kv`/depth-ar 形态
   的窗口训练（该形态的掩码语义未定义，见 2614 §3 的同类说明）。
6. **无 ERRATA**：本实验没有撤回任何先前结论；唯一需要登记的「口径发现」是
   `window32` 的 release 口径是 OOD 且**不稳定**（两次 12k 重跑差 0.066 bpc），
   已写进 `results.json::criteria` 的 `secondary_native_reference.note` 与 `stability.md §3.2`。

### 9.1 省算力侧的核算（SCHEMA §17.9）

本干预在**推理期不引入任何额外算子**（同架构、同参数量），它的「省算力」来自
**可见集变小**：native 掩码下放行的因果 (query, key) 对 = 9,460 / 32,896 = **28.76%**
（即 71.24% 的被砍掉）。⇒ 不存在「理论降幅大、实测反而变慢」的回退问题（没有离开
融合核的新算子，SDPA 只是多一个 bool 掩码）。**唯一的成本在训练期**：步时
38.4 vs 37.2 ms = **1.03×**（一次性）。所以本实验不存在需要报的**成本交叉点**：
部署侧只要把窗口外的 KV 丢掉就是**严格更快**，代价全部是质量（判据①）与保留（判据③）。
